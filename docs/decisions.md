# 의사결정·실험 기록

최종 내용 갱신일: 2026-11-27

현재 계약·범위의 정본은 [요구사항](requirements.md), 현재 진행 상태의 정본은 [프로젝트 맥락](project-context.md)이다. 이 문서는 판단 근거와 의미 있는 실험 결과를 남긴다. 모든 대화·명령·커밋을 그대로 복사하는 일지는 아니다.

## 기록 규칙

- 결정 상태는 제안·검토 중·채택·보류·기각·대체됨으로 구분한다. 구현·검증 상태는 별도로 적는다.
- 기존 결정을 바꿀 때는 새 근거와 관련 항목을 연결하고 이전 결정은 대체됨으로 표시한다.
- 가설과 관찰 사실을 구분하고, 수행하지 않은 실험·테스트·측정값·커밋 해시를 만들지 않는다.
- 같은 작업·세션·커밋의 내용을 중복 항목으로 추가하지 않는다. 기존 항목에 결과를 합친다.

## D-001 — 프로젝트의 주된 목표

- 날짜: 2026-11-21
- 상태: 채택 — 사용자 명시
- 근거: 사용자는 광고 SDK의 역할과 해결해야 할 문제를 이해하고, 깊이 고민하고 개선하며 경험을 쌓는 것이 주된 목표라고 밝혔다.
- 결정: 기능 완성과 채용 결과물에 더해 문제 정의·책임 경계·가설·비교·검증·개선 경험을 축적한다. 채용 준비는 초기 마일스톤의 맥락으로 둔다.
- 영향: 단순성은 비교 실험을 금지하는 규칙이 아니라 질문 하나를 검증하는 최소 실험의 기준으로 사용한다. 기존 요구사항·학습 내용을 이 목표에 맞게 정리했다.
- 구현·검증 상태: 문서에 반영. 광고 SDK 코드 구현·동작 실험은 미수행.

## D-002 — 네 가지 구현 원칙의 프로젝트 적용

- 날짜: 2026-11-21
- 상태: 적용 — 목표에 맞춘 작업 지침 구체화
- 판단: 가정 명시·단순성·필요한 변경·목표 기반 검증은 적합한 기본 원칙이다. 탐구의 깊이, 학습 실험, 결과·한계 기록을 추가해야 장기 목표를 충분히 지원한다.
- 적용: 코딩 전 문제·책임·가설을 설명하고, 필요한 최소 비교 실험을 허용하며, 변경의 근거를 연결하고, 검증 결과를 다음 결정으로 환류한다.
- 한계: 지침 자체가 품질을 보장하지 않는다. 선택한 계약이 문제에 맞는지와 실제 실행 근거를 별도로 평가한다.

## D-003 — 살아있는 문서 관리

- 날짜: 2026-11-21
- 상태: 채택 — 종료 시 문서 갱신은 사용자 명시, 파일 분리는 관리 방식으로 적용
- 결정: 의미 있는 작업 종료·세션 인계·커밋 작성 전후에 `AGENTS.md`와 관련 `docs`를 점검하고 변화가 있으면 갱신한다.
- 적용: `AGENTS.md`를 핵심 목표·원칙·문서 라우팅·갱신 절차로 정리하고, 기존 상세 내용을 주제별 문서로 옮겼다.
- 검증: 6개 문서의 구성·상대 링크, 기존 28개 참고 URL 보존, 핵심 목표·현재 미구현 상태, 루트 지침의 200줄·32KiB 미만 여부를 검사해 통과했다. SDK 실행 검증은 수행하지 않았다.
- 다음 질문: 첫 배너에서 해결할 문제와 성공 조건을 정하고, 재요청·해제·노출의 세부 계약을 검토한다.
- Git 상태: 이번 작업에서 커밋은 생성하지 않았다.

## D-004 — 초기 프로젝트 세팅

- 날짜: 2026-11-21
- 상태: 세팅에 적용 — 사용자 프로젝트 세팅 요청 범위에서 초기 구성을 선택. 광고 세부 정책 합의와 구분한다.
- 문제·주체: SDK 연동을 검토할 개발자에게 실행 가능한 라이브러리·호스트 앱 경계가 필요했다. 문서에는 프로젝트 미생성으로 기록돼 있었지만 실제 루트에는 Activity 없는 `:app` 템플릿이 있었다.
- 책임: SDK는 광고 기능을, 샘플 앱은 화면·연동을 맡는다. 서버는 이후 공급 응답·트래킹 수신을 맡도록 검토하되 이번 세팅에서 구현하지 않는다.
- 가설·완료 기준: `:ad-sdk` Android Library와 `:sample-app`을 연결해 APK·AAR를 생성하고 시작 화면을 실행하면, 첫 배너 계약을 구현할 최소 기반을 확보할 수 있다. 이 검증은 광고 기능 검증을 대신하지 않는다.
- 관찰: 기존 AGP 8.12.3·Kotlin 2.0.21·compileSdk 36 구성에서 `:app:assembleDebug`를 실행했다. Core KTX 1.19.1이 API 37·AGP 9.1 이상을 요구해 `checkDebugAarMetadata`가 실패했다. Kotlin 2.0.21도 현재 Gradle·AGP 조합이 공식 완전 지원 범위 밖이었다.
- 대안: API 37·AGP 9 계열로 전체 도구를 올리거나, 설치된 API 36·JDK 17에 맞춰 의존성을 고정할 수 있다. 이번 질문은 최신 도구 이전이 아니라 SDK·호스트의 최소 실행 기반 확인이므로 후자를 선택했다.
- 선택: Gradle 8.13은 유지하고 AGP 8.11.1·Kotlin 2.2.21·Core KTX 1.17.0·AppCompat 1.7.1·Material 1.13.0으로 고정했다. 기존 minSdk 26·바이트코드 11·앱 패키지·Views/XML 자산을 활용했다. SDK namespace는 `io.github.junyoungwon.adsdk`로 분리했다. 네트워크·이미지·코루틴 의존성과 공개 API는 후속 계약 검토 때 결정한다.
- 구현: `app/`을 `sample-app/`으로 옮기고 라이브러리 의존성을 추가했다. SDK는 매니페스트·빌드 설정 골격이며 광고 클래스가 없다. 샘플에 런처 Activity와 시작 화면을 추가하고 시스템 바 여백을 처리했다. 의미 없는 템플릿 테스트는 제거하고 테스트 도구 구성만 남겼다. 로컬 경로·캐시·`.DS_Store`는 Git에서 제외한다.
- 실제 검증: JBR 17.0.12/macOS ARM64에서 `:sample-app:assembleDebug :ad-sdk:assembleDebug :sample-app:lintDebug :ad-sdk:lintDebug :sample-app:testDebugUnitTest :ad-sdk:testDebugUnitTest` 실행 성공. APK·AAR 생성과 Lint 오류 0개를 확인했다. Lint 새 버전 안내 경고는 7개이며 선택한 버전을 유지한다. 테스트 코드는 없어 단위 테스트 작업은 두 모듈 모두 `NO-SOURCE`다.
- 실행 관찰: 기존 `Small_Phone_API_34` ARM64 에뮬레이터에서 설치·런처 Activity 실행 성공. 화면 캡처로 한글 제목·미요청 상태 문구가 실제 표시됨을 확인했다. Android CLI의 레이아웃 출력에서는 한글이 `?`로 나타났으나 캡처상 정상이다. CLI로 분리 실행한 에뮬레이터 연결이 유지되지 않아 프로세스 세션을 유지하는 방식으로 재실행했다.
- 한계: SDK는 아직 빈 라이브러리다. 모듈 의존·패키징·시작 화면만 검증했으며 광고 요청·광고 표시·이벤트·해제, API 26·36 실행, R8 활성화·외부 앱 AAR 연동은 미검증이다. minSdk 26은 영구 제품 지원 범위의 합의가 아니다.
- 다음 질문: 로드 완료에 포함할 준비 범위, 로드 중 재요청, 해제 이후 호출·콜백, 테스트에서 제어할 서버 응답을 어떻게 계약으로 정의할 것인가?
- 관련: [README](../README.md), [요구사항](requirements.md), [현재 상태](project-context.md). 초기 세팅 검증 시점에는 커밋·푸시를 수행하지 않았다. 후속 사용자 요청에 따라 세팅 파일·검증 결과·관련 문서를 첫 커밋에 포함하며, 실제 커밋 결과는 Git 이력으로 확인한다.
- 일차 자료: [Android Library와 앱 모듈 의존성](https://developer.android.com/studio/projects/android-library), [AGP 8.11의 Gradle·JDK·API 호환 조건](https://developer.android.com/build/releases/agp-8-11-0-release-notes), [Kotlin Gradle Plugin 호환 표](https://kotlinlang.org/docs/gradle-configure-project.html). 실제 Core 버전 충돌 판단은 빌드 오류를 근거로 했다.

## D-005 — 첫 이미지 배너의 로드·광고 표시·해제

- 날짜: 2026-11-22
- 상태: 적용·검증 — 사용자가 첫 기능 브랜치에서 작업 시작을 요청했다. 로드·광고 표시 API 분리는 사용자 선택이며, 그 외 아래 정책은 이번 구현의 초기 선택이다.
- 문제·주체: 연동 개발자가 광고 데이터 수신과 이미지 준비 완료를 혼동하지 않고 광고 표시 시점을 제어해야 한다. 이전 요청이나 화면 사용 종료 후의 결과가 현재 View·콜백에 반영되면 호스트 화면 상태를 깨뜨린다.
- 책임: SDK는 요청·응답 검증·이미지 준비·명시적 View 반영·결과 알림·해제를 맡는다. 호스트는 로드·광고 표시 시점과 사용 기간을 정하고, 모의 서버는 지면 하나의 광고·실패 응답을 공급한다. 노출·클릭·트래킹은 후속 기능이다.
- API 대안: `load()` 후 자동 반영은 연동이 간단하지만, 사용자는 준비 후 별도 `show()`로 광고 표시 시점을 제어하는 방식을 선택했다. 상태·사용 순서 설명이 추가로 필요하므로 준비 전 `show()`는 false, 준비 후에는 이미지 바인딩 결과만 반환하도록 정했다. 가시성·노출 성공으로 표현하지 않는다.
- 재요청·해제 선택: 새 `load()`는 이전 작업·이미지를 버리고 교체한다. 최신 요청만 결과를 전달하도록 취소와 요청 세대 확인을 함께 사용했다. `destroy()`는 최종·멱등 동작이며 이후 로드는 무시한다. 공개 호출과 콜백은 메인 스레드로 한정했다. 상세 정본은 [요구사항](requirements.md#첫-배너에-적용한-계약)이다.
- 최소 구조: 공개 View·요청·리스너·오류 모델, Android와 분리된 로드 완료된 광고를 관리하는 세션, HTTP 소스·이미지 어댑터로 구성했다. 세션의 준비 함수·스코프를 테스트에서 제어해 취소를 무시하는 작업의 늦은 결과까지 검증한다. 호스트 전역 이미지 로더를 변경하지 않고 View가 자신의 로더·작업 수명을 소유한다.
- 도구 선택: HTTP·연결·취소는 OkHttp 4.12.0, 디코딩·크기 조정은 Coil 2.7.0, 비동기는 Coroutines 1.10.2에 맡겼다. 두 필드 JSON은 kotlinx.serialization JSON 1.9.0의 트리 파싱을 사용해 별도 코드 생성 플러그인을 추가하지 않았다. 목표는 네트워크·디코더 재구현이 아니라 SDK 계약 검증이다. 캐시·복잡한 재시도 엔진은 만들지 않았다.
- 모의 환경: Python 표준 라이브러리 서버가 `adId`·`imageUrl`, 합성 PNG와 실패 시나리오를 제공한다. 지면은 `demo-banner` 하나다. Debug 호스트의 루프백 HTTP 예외와 ADB reverse를 사용하며 SDK가 전역 보안 정책을 완화하지 않는다.
- 발견·가설 수정: 초기의 “자동 재시도를 하지 않으려면 HTTP 연결 복구도 끈다”는 선택으로 Python 서버의 정상 이미지 로드가 `unexpected end of stream`으로 실패했다. 메타데이터 응답 후 닫힌 풀 연결 재사용이 원인이었다. 동일한 HTTP/1.0 연결 종료 조건을 기기 회귀 테스트로 만들었고 수정 전 실패를 확인했다. OkHttp 기본 연결 복구를 유지하도록 바꾼 뒤 회귀 테스트와 실제 Python 서버 연동이 성공했다. SDK의 자동 `load()` 재호출과 HTTP 연결 복구는 별개이며, 콜백 한 번이 HTTP 요청 한 번을 보장하지 않음을 계약에 남겼다.
- 실제 검증: JBR 17.0.12/macOS ARM64, API 34 ARM64 에뮬레이터. SDK 단위 테스트 16개, 샘플 호스트 기기 통합 테스트 4개 통과. 최종 `testDebugUnitTest`·두 모듈 Debug 빌드·`connectedDebugAndroidTest`·두 모듈 `lintDebug`를 `--no-watch-fs`로 실행해 성공했다. Lint 오류 0개이며 SDK에는 새 버전 안내 경고 12개가 남는다. 샘플 Lint 이슈는 없다.
- 실제 시연: Python 모의 서버·ADB reverse를 연결해 로드 완료 시 빈 배너 영역, 별도 광고 표시 버튼 후 합성 이미지·광고 라벨을 캡처로 확인했다. 테스트는 실제 광고망 E2E가 아닌 로컬 HTTP·SDK·샘플 연동 검증이다. 테스트 서버의 `localhost`/허용 주소 불일치도 발견해 테스트 URL을 `127.0.0.1`로 맞췄다.
- 한계·다음 질문: API 26·36 실행, R8 활성화·외부 AAR 소비, 화면 이동·회전·백그라운드의 전체 수명 시나리오는 미검증이다. 현재 View 바인딩과 실제 화면 광고 표시·노출을 어떻게 구분할지, 호스트의 명시적 해제가 충분히 사용하기 쉬운지 추가 관찰한다. 로드·광고 표시 분리만으로 별도 프리로드·만료·소비 정책을 완성한 것은 아니다.
- 관련: [BannerAdView](../ad-sdk/src/main/java/io/github/junyoungwon/adsdk/BannerAdView.kt), [단위 테스트](../ad-sdk/src/test/java/io/github/junyoungwon/adsdk/internal/BannerLoadSessionTest.kt), [기기 통합 테스트](../sample-app/src/androidTest/java/io/github/junyoungwon/androidadsdkplayground/BannerIntegrationTest.kt), [연동·실행 가이드](../README.md). 당시 `feat/banner-load-and-display`의 변경은 미커밋이었으며 병합·푸시는 수행하지 않았다. 후속 커밋 정리는 D-009를 따른다.

## D-006 — 사용자 코드 검토와 회전 실험 지원

- 날짜: 2026-11-23
- 상태: 코드 검토 피드백·실험 도구 적용. 재로드 중 기존 광고 유지 제안은 별도 변경으로 보류 — 사용자 선택.
- 문제·주체: 사용자가 정상 흐름·기대 동작·테스트 주석을 작성했으나 실행 위치와 자원 소유권이 모호했고, 빠른 응답 때문에 로딩 중 회전을 재현하기 어려웠다.
- 검토: suspend 호출이 자동으로 Default에서 실행되는 것은 아니다. 현재 View·세션·완료 콜백은 Main, HTTP 콜백·본문 읽기는 OkHttp 작업 스레드, JSON 파싱은 Default, Coil의 fetch·decode 기본 설정은 IO다. 처리 주체와 주입 자원의 수명 책임을 분리해 [학습 계획](learning-plan.md)에 정리했다. Coil 2.7.0 Maven sources JAR의 ImageLoader·DefaultRequestOptions를 확인한 코드 기반 설명이다.
- 기대 동작 정정: destroy는 최종 해제이며 별도 취소 콜백을 내지 않는다. 보이지 않는 View가 메모리에 없다는 뜻은 아니며 현재 show는 가시성을 검사하지 않는다. onLoaded에서 샘플이 활성화하는 것은 광고 표시 버튼이다. URL 구문·필드 오류와 유효한 URL의 이미지 다운로드·디코딩 실패를 구분한다.
- 테스트 가독성: 기존 단위 16개·기기 4개 테스트 이름을 한글·밑줄로 변경하고 사용자 주석을 실제 assert 범위에 맞춰 보완했다. 응답 검증을 'HTTP 요청을 보내지 않음'과 구분하고, 준비 대역 테스트를 실제 이미지 렌더링 검증으로 표현하지 않았다. 이후 한글 테스트 작성 규칙을 지침에 반영했다.
- 대안·선택: SDK 내부 대기를 추가하거나 제한 시간을 늘리면 검증 대상 동작까지 바뀐다. 모의 서버의 광고 데이터 응답을 delayMs=0~4000으로 제어하고 샘플 SeekBar에서 설정하도록 선택했다. slow의 기존 8초 시간 초과 조건은 유지했다. 회전 후 지연값을 복원하고, 화면별 ID와 BannerSample 로그로 요청·성공·실패·종료를 관찰한다.
- 재로드 대안: 사용자는 기존 표시 A를 유지하고 준비된 B를 show할 때 교체하는 방안을 제안했다. 빈 영역을 줄일 수 있으나 현재 표시·새 준비 광고의 식별·수명·메모리와 show 결과를 구분해야 한다. 효과·노출·수익 유지까지 보장하는 제안은 아니다. 사용자는 이번에는 회전 실험을 먼저 하고 별도 정책 변경으로 진행하기로 선택했다. SDK의 재로드 즉시 제거 계약은 바꾸지 않았다.
- 실제 검증: 단위 테스트 16개, API 34 ARM64 기기 테스트 5개 통과. 추가 기기 테스트는 응답을 gate로 대기시켜 ActivityScenario.recreate()를 수행하고, 이전 Activity 종료·이전 리스너 결과 없음·이전 View의 추가 load 무시·새 View 재로드·지연 설정 복원을 확인했다. URL 헬퍼의 MockWebServer.url()이 메인에서 역방향 호스트명 조회를 유발한 테스트 인프라 문제를 발견해 루프백 HttpUrl을 직접 조립하도록 수정했다. Debug APK 빌드·두 모듈 Lint 오류 0개, SDK 버전 안내 경고 12개를 확인했다.
- 모의 서버 검증: 기존 8080 프로세스를 유지한 채 새 코드를 8081에서 실행했다. delayMs=0은 약 10ms, 500은 약 507ms에 응답했고 잘못된 지연값 세 종류는 HTTP 400이었다. 새 UI의 지연 제어·화면 ID 표시를 캡처로 확인했다.
- 한계·다음 판단: 자동 재생성 테스트는 물리적 방향 전환·모든 화면 수명·GC/메모리 누수 검증을 대신하지 않는다. 이전 리스너 미전달은 테스트 관찰 구간과 기존 세션 취소 테스트 근거로 평가한다. 사용자가 직접 회전 실험을 수행한 결과는 아직 받지 않았다. 서버 코드 변경은 실행 프로세스 재시작이 필요하다.
- 관련: [샘플 화면](../sample-app/src/main/java/io/github/junyoungwon/androidadsdkplayground/MainActivity.kt), [모의 서버](../mock-server/server.py), [기기 테스트](../sample-app/src/androidTest/java/io/github/junyoungwon/androidadsdkplayground/BannerIntegrationTest.kt), [README](../README.md). 커밋·병합·푸시는 수행하지 않았다.

## D-007 — 지연 설정을 무시하던 구버전 서버 프로세스

- 날짜: 2026-11-23
- 상태: 재현·환경 수정·재검증 완료.
- 문제: 사용자는 3초 설정에도 광고 표시 버튼이 거의 즉시 활성화된다고 보고했다. 앱 로그에서도 delay=3000ms 요청이 수십 ms 만에 성공했다.
- 관찰·원인: 앱 기본 주소 8080에는 지연 기능 추가 전부터 실행된 이 프로젝트의 Python 서버가 남아 있었다. 소스 파일 수정은 실행 프로세스에 자동 반영되지 않는다. 동일한 delayMs=3000 요청에서 8080은 0.002540초, 최신 서버인 8081은 3.025452초였다. 앱이 전달한 지연값은 정상이었고, 오래된 서버가 쿼리를 무시했다. 이전 검증을 8081에서 수행하면서 기본 8080 프로세스를 남긴 인계 방식이 혼동의 원인이었다.
- 조치: 명령·포트·작업 디렉터리로 구버전 개발 서버(PID 67966)를 확인한 뒤 종료하고, 최신 mock-server/server.py를 기본 8080에서 다시 실행했다. SDK·슬라이더·지연 로직은 변경하지 않았다.
- 검증: 재시작한 8080의 같은 요청은 3.008127초에 응답했다. 실행 중인 샘플에서 3000ms로 로드를 재실행했고, 같은 화면·요청의 시작 19:07:13.093 → 성공 19:07:16.394로 약 3.301초를 확인했다. 전체 시간은 이미지 준비 등을 포함한다. 코드 변경이 없어 단위·기기 테스트 전체 재실행은 하지 않았다.
- 후속: README에 실제 응답 시간을 측정하는 진단 명령과 서버 재시작 필요를 보완했다. 개발 서버 프로세스·앱 주소·ADB reverse를 실행 환경의 일부로 확인한다. 커밋·병합·푸시는 수행하지 않았다.

## D-008 — 사용자의 로딩 중 회전 관찰과 취소 경로 검토

- 날짜: 2026-11-23
- 상태: 사용자 실험 결과 검토·설명 완료. 회전 시 로드 유지 설계는 후속 대안이며 구현하지 않았다.
- 사용자 실험: 정상 시나리오의 로드 시작·성공을 비교 기준으로 삼고, 3~4초 응답 지연 중 회전 시 이전 화면 종료(구성 변경=true)·새 화면 생성·미로드 상태를 관찰했다. 사용자가 readAdBody의 invokeOnCancellation에 진단 로그를 추가했고, 회전 시 해당 핸들러가 실행되는 로그를 제공했다. 이 기록은 사용자 제공 관찰이며 에이전트가 같은 물리적 회전을 재실행한 결과는 아니다.
- 코드 연결: Activity.onDestroy → BannerAdView.destroy → 세션 Job.cancel·View Scope.cancel → 취소 가능한 HTTP 대기 continuation 취소 → 등록된 Call.cancel 경로와 일치한다. 현재 Scope는 수동 생성한 Scope이므로 Activity 파괴 자체가 자동으로 취소하는 것이 아니라 명시적 해제가 연결을 만든다.
- 관찰 해석·한계: UI 초기화만으로 요청 취소를 확정할 수 없지만, 추가 핸들러 로그는 HTTP Call.cancel 호출 경로에 도달했다는 근거다. 서버 응답 지연은 광고 데이터 단계이므로 이번 실험은 메타데이터 대기 중 취소 검증이다. 서버 처리 중단, 메모리의 즉시 회수·누수 없음, 이미지 요청·디코딩 중 취소와 모든 경합 시점까지 확인한 것은 아니다. '저장 상태 복원=true'도 로드 완료된 광고 복원을 의미하지 않는다.
- 취소 시점 검토: invokeOnCancellation은 주기적 상태 조회가 아니라 취소 이벤트 핸들러 등록이다. 외부 HTTP 작업을 시작하기 전에 등록하는 위치가 적절하다. onResponse의 response.use와 isActive, continuation의 취소 가능한 재개, 세션의 ensureActive·해제·세대 확인이 서로 다른 경계에서 결과 정리·전달을 제어한다. HTTP 대기가 이미 끝나 이미지 준비 단계에 있다면 이 핸들러 로그가 안 나와도 로드 작업은 취소될 수 있다.
- 수명 대안: 회전 중 준비를 유지하려면 UI와 분리된 로더·상태·로드 완료된 광고를 더 긴 수명의 소유자에 둔다. 호스트 ViewModel은 후보이며 SDK가 ViewModel을 필수 의존하도록 만들 필요는 없다. 이전 View·Activity·그것을 캡처한 콜백을 보관하지 않고 새 화면이 상태를 구독해 새 View에 연결해야 한다. 기존 구조에서 destroy를 생략하거나 Scope만 옮기는 변경으로는 이 분리가 완성되지 않는다.
- onDestroy 한계: 프로세스 종료 때는 정상 취소·해제 콜백이 보장되지 않으며 같은 프로세스의 코루틴·스레드도 더 실행되지 않는다. 서버의 이미 수신한 처리가 취소됨을 뜻하지 않는다. 반면 프로세스가 살아 있고 화면만 안 보이는 상태에서는 현재 구현이 자동 취소하지 않으며, 해제 호출 누락에 대한 일반 보장도 없다. 화면 비가시 시 중지 정책은 별도 계약이다.
- 실제 추가 확인: 현재 진단 로그를 포함한 BannerHttpSourceTest 9개를 실행해 통과했다. 전체 단위·기기 테스트 재실행, 새 물리적 회전·프로세스 종료·메모리 측정은 수행하지 않았다. 사용자 소스의 진단 로그는 유지했고 제품 코드·정책·커밋·병합은 변경하지 않았다.
- 참고: [취소 가능한 콜백 대기](https://kotlinlang.org/api/kotlinx.coroutines/kotlinx-coroutines-core/kotlinx.coroutines/suspend-cancellable-coroutine.html), [invokeOnCancellation](https://kotlinlang.org/api/kotlinx.coroutines/kotlinx-coroutines-core/kotlinx.coroutines/-cancellable-continuation/invoke-on-cancellation.html), [Activity·프로세스 수명](https://developer.android.com/guide/components/activities/process-lifecycle), [ViewModel](https://developer.android.com/topic/libraries/architecture/viewmodel).

## D-009 — 기능 커밋 분리와 원격 PR 작업 방식

- 날짜: 2026-11-24
- 사용자 요청: 원격 저장소는 사용자가 생성 후 링크를 제공한다. 초기 세팅의 main만 먼저 업로드하고, 기능 브랜치는 PR로 병합한다. 먼저 기능 브랜치의 로컬 커밋 분리를 요청했고, 이후 원격 저장소 링크를 전달했다.
- 분할 기준: 검토할 동작과 이를 검증하는 테스트·계약 문서를 함께 묶는다. SDK·단위 테스트·공개 계약, 모의 서버·샘플·기기 통합 테스트·실행 가이드, 학습·판단 기록·작업 지침의 세 단위로 나눈다. 의존 순서는 SDK → 샘플 연동이며 각 커밋의 문서는 그 시점의 구현 상태에 맞춘다.
- 발견·조치: 커밋 전 기기 테스트에서 화면 재생성 후 이전 리스너 결과 차단 검증이 실패했다. 현재 MainActivity.onDestroy의 banner.destroy()가 주석 처리된 상태였으며, 기존 해제 계약에 맞게 호출을 복원했다. 사용자 설명 주석과 HTTP 취소 진단 로그는 유지한다. SDK 정책을 변경하거나 회전 중 로드를 유지하는 설계를 도입한 것은 아니다.
- 환경: Android CLI의 에뮬레이터 시작 완료 후 기기 연결이 사라져 첫 기기 검사 시도가 실행되지 않았다. 에뮬레이터를 직접 실행해 연결·부팅 완료를 확인한 뒤 테스트를 실행했다. 연결 실패와 실제 테스트 실패를 구분한다.

## D-010 — 재로드 중 기존 광고 유지의 검증 기준

- 날짜: 2026-11-24
- 상태: 2026-11-24의 재현과 대안 비교 기록. 이후 사용자 선택과 구현 결과는 D-011을 따른다.
- 시작 상태: 사용자가 PR #1을 병합한 뒤 로컬 main을 갱신하고 feat/retain-banner-on-reload를 생성했다. 로컬 main·origin/main과 새 브랜치의 시작 커밋이 01b126e이며 작업 트리가 깨끗함을 확인했다.
- 문제: 현재는 A 표시 중 B를 요청하면 A를 즉시 지운다. B 응답이 늦거나 실패하면 빈 광고 영역이 이어진다. 목표는 B 준비 중과 준비 완료 후 show 전까지 A를 유지하고, show에서 B로 교체하는 것이다. 광고 효과나 수익 유지까지 보장하는 개선은 아니다.
- 미정 계약: 처음 질문한 show는 SDK 사용자가 호출하는 BannerAdView.show였으며, 현재는 Session.show의 값을 그대로 반환한다. 사용자는 Session의 false로 가장 최근에 로드 완료된 광고 부재를 구분하는 데 동의했고, View에서는 기존 광고를 표시할 수 있는 경우에도 true를 반환하는 방안을 제안했다. 공개 계약은 비교 중이며 이 선택에 의존하는 제품 구현은 진행하지 않는다.
- 비교: 내부 함수와 공개 함수의 반환 의미가 달라도 계층별 책임이 분명하면 구현할 수 있다. 다만 공개 true가 새 이미지 반영과 기존 이미지 유지를 함께 뜻하면 호출자는 교체 여부를 구분할 수 없다. 반대로 최신 이미지 반영만 성공으로 보면 false여도 A가 남을 수 있으므로 호스트가 이를 빈 광고 영역으로 해석하지 않도록 문서화해야 한다. 두 방식 모두 실제 가시성이나 노출 성공을 뜻하지 않는다.
- 제안: 공개 show의 성공 의미를 먼저 정한 뒤 내부 함수의 이름과 책임을 맞춘다. 처음에는 가장 최근에 로드 완료된 광고 반영을 반환하는 방식을 권장했다. 이후 사용자가 현재 광고 표시 상태의 필요성은 두 방식에 공통이라고 지적했으며, 단순성만으로 앞 방식을 우위에 둔 설명을 정정했다. 현재 검토 제안은 가장 최근에 로드 완료된 광고 반영 여부와 현재 View 내용 존재 여부를 분리해 제공하는 조합이다. 내부 함수는 bindPrepared 또는 renderPrepared처럼 명명하면 공개 show와의 역할 차이를 드러낼 수 있다. 기존 A 유지까지 공개 성공에 포함하려면 보존 범위를 이미 표시한 이미지로 한정할지, 표시 전 과거 로드 완료된 광고까지 허용할지 추가로 정해야 한다. 대안 비교를 사용자 합의나 구현 완료로 기록하지 않는다.
- 시나리오 비교: 피드 하단의 빈 광고 영역만 피하려는 호스트에는 기존 광고 유지도 성공인 show가 간단하다. 정해진 UI 전환 시점에 새로 로드 완료된 광고를 반영해야 하는 호스트에는 가장 최근에 로드 완료된 광고 반영 여부가 필요하다. 갱신 실패 기록과 기존 광고 영역 유지는 동시에 필요한 정보이므로 로드 결과와 현재 내용 존재를 분리한다. 내용을 바꾸지 않고 영역 상태만 조회할 때는 두 방식 모두 별도의 조회 수단이 필요하다.
- 정보 후보: 읽기 전용 hasBoundAd는 View에 설정된 광고 이미지의 존재를 뜻하도록 제안한다. 이것은 최신 로드의 준비 상태나 실제 화면 노출과 다르다. show는 호출 결과이며 상태 조회를 위해 호출하면 준비된 B로 교체할 수 있으므로 조회용 대체재가 아니다. 한 번의 반환에 두 정보를 담아야 하는 요구가 확인되면 APPLIED_LATEST·KEPT_CURRENT·UNAVAILABLE 같은 명시적 결과도 대안이지만 아직 채택하지 않는다.
- 구조 후보와 책임: 호스트는 요청과 광고 표시 시점을 결정한다. SDK의 ImageView는 표시 중인 A를 참조하고 세션 prepared는 가장 최근에 로드 완료된 광고 B를 보관한다. load에서는 이전에 로드 완료된 광고를 버리되 표시 이미지를 지우지 않는 방식으로 기존 구조를 활용할 수 있다. A와 B를 함께 보관하는 동안 메모리 비용은 늘 수 있다. 서버 책임과 응답 계약은 변경할 필요가 없다.
- 재현: 새 기기 테스트에서 A를 표시하고 B를 로드한 직후 동일 Drawable 유지 여부를 검사했다. API 34 ARM64에서 테스트 1개를 실행했고 expected same BitmapDrawable, actual null로 실패했다. 현재 load의 clearImage 호출과 일치한다. 테스트에는 B 준비 후에도 A가 유지되고 show 뒤 빨간 새 이미지로 바뀌는 기대를 추가했지만, 이번 실행은 첫 유지 검사에서 실패했으므로 뒤 검사를 검증했다고 보지 않는다.
- 변경 범위: 기기 테스트 한 개와 색상이 다른 PNG 대역을 추가했다. 기존 정책 테스트와 제품 코드, 샘플 동작은 아직 바꾸지 않았다. 전체 테스트·Lint·최종 빌드는 미실행이며 새 테스트는 현재 실패 상태로 남아 있다. 커밋·푸시·PR 생성은 수행하지 않았다.
- 당시 다음 단계: 반환 계약 선택 후 유지 동작과 해제를 검증하고 정책과 샘플을 갱신한다. 이 작업의 실제 결과는 D-011에 기록한다.

## D-011 — 기존 광고 표시 유지와 광고 표시 결과 콜백

- 날짜: 2026-11-25
- 상태: 사용자 선택 반영, 구현과 자동 검증 완료. 이후 사용자가 기존 광고 유지와 새 show 교체에 관한 세 가지 수동 시나리오가 기대대로 동작했다고 보고했다. 전체 코드 이해 확인까지 완료했다고 기록하지 않는다.
- 사용자 선택: show는 가장 최근에 로드 완료된 광고를 반영하는 명령으로 정의한다. 기존 A가 남아 있어도 B를 반영할 수 없으면 광고 표시 실패다. 성공 시 광고 정보, 실패 시 원인을 콜백으로 전달하는 방식을 요청했으며 현재 광고 표시 상태 조회는 후속 기능으로 보류했다. D-005의 즉시 이미지 제거와 Boolean 공개 반환 계약을 대체한다.
- 책임과 구조: View.load에서 clearImage를 호출하지 않아 기존 A를 유지한다. 세션은 요청 교체 시 로드는 완료됐지만 아직 View에 반영하지 않은 광고를 버리고, 완료한 B의 광고 정보와 Drawable을 한 로드 완료된 광고로 보관한다. bindPrepared는 가장 최근에 로드 완료된 광고만 View에 전달하며 View가 반영 후 공개 성공 콜백을 호출한다. destroy는 세션 로드 완료된 광고와 표시 이미지를 함께 정리한다. HTTP 취소와 요청 세대 확인은 유지했다.
- 용어 정정: 사용자 요청으로 모호한 준비 관련 표현을 로드 완료된 광고로 명시하고, show 동작은 광고 표시로 표현한다. 노출은 노출 조건 충족과 집계의 의미로 구분한다. 리스너를 보관하지 않는다는 설명은 멤버 변수의 장기 참조와 이번 함수 호출에서의 사용을 구분하도록 보완했으며, API 이름과 실행 동작은 바꾸지 않는다.
- API 세부 선택: show(BannerAdShowListener)는 호출 안에서 메인 스레드로 성공 또는 실패 하나를 알린다. 실제 렌더링 프레임이나 노출 측정을 기다리는 비동기 이벤트로 만들지 않았다. 성공 정보는 adId와 placementId이며 이미지 객체나 서버 URL은 노출하지 않는다. 광고 표시 리스너는 이번 show의 함수 인자로만 사용하며, show 반환 이후에도 SDK가 다음 호출이나 이벤트에 사용하려고 멤버 변수에 보관하지 않는다. 다음 show에는 리스너를 다시 전달해야 하며 동일 객체의 재사용은 가능하다. 콜백이 load나 destroy를 다시 호출할 수 있고, 호스트 예외를 잡아 추가 실패 콜백으로 바꾸지 않는다.
- 실패 모델: NOT_LOADED, LOADING, LOAD_FAILED, DESTROYED를 구분한다. LOAD_FAILED에는 원래 BannerAdError를 loadError로 포함한다. 같은 load 실패를 광고 표시 성공으로 바꾸지 않고, 광고 표시 실패 때문에 A를 지우지도 않는다. 반복 show는 같은 광고를 반영하고 각 호출에 결과를 알리며, 새 광고 노출로 집계하지 않는다. 이 세부 오류 모델과 동기 콜백은 현재 구현 선택이며 광고 플랫폼 공통 표준으로 표현하지 않는다.
- 재현에서 개선까지: 11/24에 추가한 A 유지 테스트는 기존 load의 clearImage 때문에 실제 Drawable 대신 null을 받아 실패했다. clearImage 호출을 해제 시점에만 남긴 뒤 같은 테스트가 통과했다. 색상이 다른 PNG와 서로 다른 adId를 사용해 B 준비 전후 A 유지, show 이후 B 이미지와 B 광고 정보의 일치를 확인했다.
- 검증: SDK 단위 테스트 18개, API 34 ARM64 기기 통합 테스트 10개 통과. Debug AAR·APK 빌드 성공, 두 모듈 Lint 오류 0개이며 SDK 버전 안내 경고 12개는 남는다. NoFill과 디코딩 실패 후 A 유지, 실패 사유와 원인 전달, 아직 광고 표시하지 않은 로드 완료된 광고 폐기, 광고 표시 중인 이미지와 로드 완료된 광고가 함께 있을 때 해제, 콜백 안에서 해제와 재로드를 확인했다. 실제 메모리 회수, 새 수동 시연, 모든 생명주기와 API 26·36 실행은 이번에 검증하지 않았다.
- 샘플과 문서: 샘플은 새 성공 콜백으로 반영한 adId를 표시하고 실패 이유를 안내한다. 광고 표시 버튼은 여전히 로드 성공 후 활성화한다. README 연동 예시와 수동 재현 절차를 갱신했다. 기존 모의 서버는 같은 그림을 반환하므로 수동으로는 이미지 차이가 아닌 반영한 광고 ID를 참고한다. 서버 코드는 변경하지 않았다.
- 사용자 수동 확인: 서버 복구 후 사용자는 앞서 안내한 세 시나리오인 B 로딩 중/준비 후 show 전 A 유지, B 실패 시 A 유지, show 성공 시 반영한 B 정보 전달이 기대대로 동작했다고 보고했다. 사용자 제공 결과이며 에이전트가 새로 수행한 자동 검사나 측정으로 기록하지 않는다.
- 남은 질문: 정리한 show 계약을 검토하고, A를 유지하는 동안 B의 준비 참조가 어떻게 바뀌는지 설명해 본다. 광고 표시 상태 조회, 실제 노출과 추적, 회전 중 로드 유지, 캐시와 자동 갱신은 별도 검토다. 이번 작업에서 커밋·푸시·PR 생성은 수행하지 않았다.

## D-012 — 반복 show와 노출 중복 방지의 경계

- 상태: 현재 코드 확인과 학습 설명 완료. 노출 집계나 부정 트래픽 방지 구현은 착수하지 않았다.
- 사용자 질문: 새 load 없이 show를 반복해 성공 콜백이 늘어나면 같은 광고의 노출과 수익을 부풀릴 수 있는지 확인했다.
- 현재 사실: 로드 완료된 광고는 show 후 소비되지 않으므로 같은 광고를 다시 반영하고 같은 adId로 성공을 알린다. 미로드, 새 로드 진행 중, 새 로드 실패, 해제 후에는 각각의 실패를 알린다. SDK에는 노출 판정·노출 콜백·전송 코드가 없고 모의 서버에도 이벤트 집계가 없다. 기존 '노출로 집계하지 않는다'는 설명은 중복 방어가 구현됐다는 뜻이 아니라 집계 자체가 미구현이라는 뜻으로 정정했다. 이전 기기 테스트가 반복 show의 동일 정보 성공을 확인했으며 이번 설명에서는 테스트를 재실행하지 않았다.
- SDK 설계 후보: 노출 조건을 만족하는 표시 광고 제공 건에 논리적 이벤트 생성 여부를 묶는다. 반복 show 또는 B 로드 시작으로 A의 표식을 초기화하지 않는다. 콜백 재진입 전에 생성 여부를 기록하고 전송 재시도는 같은 이벤트 식별자를 사용한다. 현재 ImageView가 가진 Drawable 외에도 표시 광고의 식별과 추적 수명을 관리할 필요는 후속 구현 시 검토한다.
- 서버 설계 후보: 서버가 발급한 제공 건과 앱·지면 등의 연결 및 유효 기간을 확인하고, 제공 건과 이벤트 종류의 유일성을 저장소에서 원자적으로 보장한다. 클라이언트가 다른 이벤트 ID를 붙여 재전송해도 같은 제공 건을 여러 번 집계하지 않는다. 단순 소재 ID로 중복을 제거하지 않는다. 토큰이나 서명은 발급과 변조 검증의 수단이며 실제 노출의 증거는 아니다.
- 한계: 클라이언트의 플래그나 show 반복 거절만으로 악의적 호스트를 신뢰할 수 있게 되지는 않는다. 새 제공 건을 계속 받는 행위는 동일 건 중복 제거로 해결되지 않아 별도 이상 활동 분석이 필요하다. Google의 공개 무효 트래픽 설명은 이런 문제의 존재를 확인하는 자료이며 위 설계가 AdMob 내부 구현이라고 주장하지 않는다.
- 후속 검증 후보: 준비 광고에 show를 반복해도 조건 충족 이벤트는 한 번, 비가시 상태에서는 show 성공과 별개로 노출 0회, A 표시 중 B 로드 실패 시 A 중복 이벤트 없음, 같은 제공 건의 재전송이나 다른 View 재사용도 서버 집계 한 번을 확인한다. 모두 후속 제안이며 이번 검증 결과가 아니다. 기존 표시 콜백 계약을 단일 사용으로 바꾸거나 현재 브랜치에 트래킹 범위를 추가하지 않았다.

## D-013 — 종료된 모의 서버와 누락된 기기 연결 복구

- 날짜: 2026-11-25
- 상태: 실행 환경 복구와 앱 로드 성공 확인 완료. 제품 코드는 변경하지 않았다.
- 제보와 관찰: 사용자가 NETWORK의 Ad request failed를 보고했다. 개발 컴퓨터에서 8080·8081 리스너가 없었고 연결된 API 34 기기의 adb reverse 목록도 비어 있었다. 샘플 화면은 127.0.0.1:8084 연결 실패를 표시했으며 주소 입력값도 8084였다. 기존 프로세스의 종료 원인까지 확인한 것은 아니다.

- 인계: 모의 서버는 실행 중이며 기기 연결은 8080과 8084를 모두 개발 컴퓨터 8080으로 전달한다. 프로세스 실행과 reverse는 저장소의 소스 파일만으로 유지되지 않으므로 서버나 기기 연결이 종료되면 다시 확인한다. README에 Failed to connect 진단과 서로 다른 기기/컴퓨터 포트 연결 예시를 추가했다. 코드 변경이 없어 단위·기기 테스트 전체를 재실행하지 않았고 커밋·푸시도 수행하지 않았다.

## D-015 — 배너 노출 판정의 계약 검토

- 날짜: 2026-11-26
- 상태: 계약 검토 후 사용자가 이미지 영역 50% 이상 연속 1초, 창 포커스가 있을 때만 판정, View 단위 리스너 등록을 선택했다. 이를 반영한 SDK와 샘플, 테스트를 구현했다.
- 시작 상태: 사용자가 PR #2를 병합하고 생성한 feat/banner-impression-detection을 확인했다. main·origin/main과 새 브랜치의 시작은 a2f6e45이고 작업 시작 시 깨끗했다. 처음에는 작업 준비와 계약 검토만 수행했고, 사용자 선택 이후 구현으로 진행했다.
- 문제와 책임: show 성공만으로 노출 조건 충족을 알 수 없다. SDK는 현재 광고 표시 중인 광고를 관찰하고 동일 제공 건의 중복 알림을 막아야 한다. 호스트는 노출 이벤트를 받을 리스너와 View의 사용 기간을 관리한다. 서버 전송과 전역 중복 제거는 후속 범위다.
- 코드에서 찾은 검토 지점: ImageView는 A의 Drawable만 참조하고 세션의 prepared는 B 로드 시 초기화된다. 따라서 현재 광고 표시 중인 A의 adId와 노출 진행 상태를 세션의 최신 로드 상태만으로 관리할 수 없다. 광고 표시 중인 광고의 정보와 이미지, 노출 처리 이력을 연결해야 한다. 기존 광고 표시 리스너는 호출 안에서만 사용하지만, 노출 조건은 나중에 충족될 수 있어 별도 노출 리스너의 참조와 해제 시점을 정해야 한다.
- 사용자 결정 요청: 이미지 영역 50% 이상 연속 1초와 일부 영역의 최초 관찰 즉시 판정 중 선택, 포커스가 없는 창의 허용 여부, View 단위 또는 로드 단위 노출 리스너 등록을 질문했다. 사용자는 이미지 영역 50% 이상 연속 1초와 포커스가 있는 창만 허용하는 방식을 선택했다. 사용자는 리스너 두 등록 방식의 장단점을 질문했고, View 단위는 한 화면의 이벤트 처리가 단순하며 로드 단위는 요청별 처리를 연결하기 쉽다고 비교했다. A 유지 중 B를 로드하면 로드 단위 방식은 A와 B 리스너를 각각 보관하고 실제 광고 교체 시점에 알림 대상을 바꿔야 한다. View 단위는 모든 이벤트의 adInfo를 구분하고 등록 교체의 의미를 정해야 한다. 비교 후 사용자가 View 단위를 선택했다. 같은 View의 같은 adId에 한 번, 조건 중단 시 시간 초기화, 늦은 리스너 등록 시 소급 전달 없음, show 결과 콜백 이후 재확인은 세부 구현 계약으로 적용했다.
- 근거와 한계: Google Active View 문서의 디스플레이 조회 가능성 지표는 50%와 1초를 설명하지만 일반 노출과 구분한다. Android getGlobalVisibleRect는 root View 기준으로 잘리지 않은 사각 영역을 반환한다. 이를 임의 가림의 완전한 측정으로 해석하지 않는다. 창 포커스는 입력 포커스에 관한 상태이며, Android 문서상 Paused Activity도 다중 창에서 보일 수 있다. 이 차이를 제품 정책으로 선택해야 한다.
- 구현 이유: 현재 광고 정보와 노출 이력은 BannerAdView에 속하고, BannerLoadSession은 최신 로드의 성공과 실패를 계속 담당한다. View 조건을 계산하는 BannerVisibility와 시계를 주입하는 BannerImpressionTracker를 분리해 실제 Android 상태와 시간 경계를 각각 검증한다. 범용 이벤트 엔진이나 별도 생명주기 저장소는 추가하지 않았다.
- 시간과 수명: 프레임과 스크롤, 레이아웃, 창 상태에서 조건을 관찰하고 남은 시간에 한 번 예약해 다시 확인한다. uptimeMillis를 사용해 벽시계 변경을 피한다. detach는 진행 시간만 초기화하고 destroy는 관찰 등록, 예약 작업, 리스너와 광고 참조를 정리한다. 반복 show와 B 로드가 A의 시간이나 이력을 초기화하지 않는다.
- 중복과 콜백: 한 View가 기억하는 adId 집합으로 중복을 억제하고 콜백 전에 이력을 기록한다. 리스너가 없어도 이력을 유지해 늦은 등록의 소급 알림을 막는다. destroy 후 추가 등록은 무시한다. show의 결과 콜백 중에는 노출 알림을 중첩하지 않으며 반환 후 현재 광고와 조건을 확인한다.
- 검증: SDK 단위 테스트 27개(노출 시간 판정 9개 포함), API 34 ARM64 기기 테스트 22개(노출 연동 12개 포함)가 통과했다. 999ms와 1000ms 경계는 가짜 시계로, 이미지 면적 49%와 50%, 여백, 스크롤, 미부착, 상위 alpha 0, 숨김, 창 포커스, A 유지 중 B 실패, 리스너 등록과 교체, 해제와 재진입은 실제 View로 확인했다. Debug AAR와 APK 빌드, 두 모듈 Lint도 통과했다. 사용자의 직접 관찰과 이해 확인은 아직 수행했다고 기록하지 않는다.
- 샘플 관찰: Python 모의 서버에 연결한 API 34 샘플에서 로드 후 광고 표시와 스크롤로 노출 알림 1회를 확인했다. 같은 광고의 show 반복과 숨김 후 복귀에도 알림은 1회로 유지됐다. 이는 에이전트가 수행한 관찰이며 사용자의 검토 완료로 기록하지 않는다. 샘플의 Lint 권장사항은 isVisible 사용으로 반영해 빌드와 Lint를 재확인했다.
- 한계와 다음 질문: 사각 클리핑은 임의 덮임이나 투명 픽셀의 정확한 측정이 아니다. 회전과 배율 변환은 판정에서 제외한다. ID 이력은 View 수명 중 누적되며 다른 View와 프로세스의 중복 제거, 서버 수신과 과금은 다루지 않는다. 사용자가 직접 A/B의 광고 ID와 알림 시점을 관찰한 뒤 다음 서버 트래킹 계약을 검토한다.

## D-016 — Tracker와 View의 책임 분담 리뷰

- 날짜: 2026-11-27
- 요청과 수행: 사용자가 동의한 첫 Tracker 테스트 수정을 반영하고, Tracker와 View의 책임을 정적으로 검토했다. 초기 광고 미등록과 방어 입력을 주석으로 명시하고 고정 시각을 0으로 바꿨다. 동작 결과와 남은 시간을 변수로 받은 뒤 검증한다. 테스트 9개를 포함한 SDK 단위 테스트 전체 27개가 통과했다. 제품 동작과 공개 계약은 변경하지 않았다.
- 이해 보완: Tracker는 이미 확정한 노출의 지속 시간을 측정하는 객체가 아니다. View가 지금 확인한 가시 조건이 처음 충족된 시점부터 연속 1초를 판정하고, 현재 광고와 ID 이력으로 최초 알림 여부를 결정한다. View만으로 전체 노출을 확정하지 않는다. 업계 일반 기준이 아니라 현재 프로젝트 정책의 분담을 검토한 것이다.
- 확인한 분리: HTTP 요청과 응답 검증은 BannerHttpSource, 이미지 준비는 BannerImageLoader, 최신 로드 상태와 취소는 BannerLoadSession이 처리한다. View는 이 객체를 구성하고 결과를 이미지에 반영한다. Android 가시성 계산은 visibleImageFraction 함수에 있으며, 시간과 중복 상태는 Android 참조가 없는 Tracker에 있다. 이 분리 덕분에 시간 경계는 가짜 시계로 검증할 수 있다.
- View의 집중 지점: 관찰자 등록과 해제, 조건 확인, 다음 검사 예약, show 콜백과의 순서 제어, 노출 리스너 전달을 View가 함께 수행한다. HTTP 클라이언트와 로더의 설정, 생성과 해제도 담당한다. 위임을 했더라도 View가 관리하는 수명과 조합은 적지 않다. 독립적인 정책 변경이 View에 얼마나 영향을 주는지 검토해야 한다.
- 정책과 상태의 검토 지점: visibleImageFraction은 순수 면적뿐 아니라 창 포커스와 alpha, 변환 허용 여부도 반영한다. 예를 들어 포커스 없는 창도 판정하도록 정책을 바꾸면 이 함수를 수정해야 한다. 면적 50% 기준은 View에, 연속 1초 기준은 Tracker에 있다. 현재 광고 정보도 View와 Tracker에 있으므로 show에서 함께 갱신되고 B의 load가 A 관찰을 바꾸지 않는 관계를 유지해야 한다. 현재 경로에서 불일치를 확인한 것은 아니다.
- 판단과 제안: 단일 이미지 배너의 SDK 진입점인 View가 렌더링과 생명주기를 연결하는 현재 구조는 수용 가능하다. 노출과 로드 관련 기능이 있다는 이유만으로 책임 위반이라고 단정하지 않는다. 다만 책임 분리가 모두 끝났다고 평가하지도 않는다. 노출 관찰과 예약, 가시 조건 판단을 담당하는 Android 전용 내부 객체는 후속 분리 후보이며 Tracker의 Android 독립성은 유지한다. 그 경우 View는 부착과 해제, 광고 교체 등의 이벤트를 전달하고 최종 콜백 순서를 보장한다. 서버 전송이나 재시도는 View에 직접 추가하지 않는 방향을 권장한다. 자원 생성 구조의 분리는 공유나 설정 교체가 실제 필요해지는 시점에 별도로 판단한다.
- 한계와 다음 판단: 이번 요청에서 노출 제어 객체를 새로 만들거나 구현을 이동하지 않았다. 이 정적 책임 리뷰와 단위 테스트 통과는 화면 수명과 메모리 누수 전체를 검증한 것이 아니다. 기기 테스트는 재실행하지 않았다. 다음 구조 변경 시 관찰 중단과 재개, A/B 교체, destroy 이후 예약 작업, 콜백 재진입 계약을 다시 확인한다.
- 우선순위 제안: 이번 브랜치에서는 노출 관찰 객체 추출을 보류하고, 사용자의 대표 시나리오 직접 검토와 기능 마무리, 지원 자료 작성을 우선하도록 권장했다. 현재 리뷰에서 이 구조로 인한 계약 위반을 특정하지 않았고 시간과 중복 판단은 이미 분리돼 있다. 관찰과 예약 코드를 옮기면 수명과 콜백 순서의 재검증 비용이 생기므로 이번 지원 마일스톤에서 먼저 해결할 문제로 보지 않는다. 여유가 확보되면 다음 핵심 기능인 노출 전송과 서버 중복 수신 처리의 계약을 검토하며, 그 변경에 필요한 분리는 근거를 보고 수행한다. 구체적인 해제 누락이나 계약 위반이 발견되면 현재 브랜치에서 필요한 원인 수정을 진행한다. 이는 사용자 선택 이전의 권고이며 리팩터링 포기나 장기 확장 제한이 아니다.

## D-017 — 현재 범위의 내부 정리와 KDoc 보강

- 날짜: 2026-11-27
- 요청과 경계: 사용자가 현재 구현 범위에서 정리할 곳과 테스트, 특히 visibleImageFraction과 BannerAdView의 KDoc 점검을 요청했다. 공개 API와 노출 조건은 유지하고, 별도 관찰 객체나 네트워크 구성 계층은 도입하지 않았다. D-016의 큰 구조 분리 보류와 이번의 작은 내부 정리를 구분한다.
- 가시성 함수: 기존 화면 상태 검사를 private isImpressionObservationAllowed로 모아 면적 계산과 읽는 위치를 구분했다. visibleImageFraction의 반환 의미는 유지한다. KDoc에는 FIT_CENTER의 빈 여백 제외, root 좌표로 맞춘 이미지와 클리핑 사각형의 교집합 계산, 판정 제외도 0이라는 의미를 명시했다. 창 포커스와 회전, 배율, alpha 정책 및 임의 가림과 투명 픽셀 측정의 한계도 설명했다. 이 함수가 완전히 순수한 면적 함수로 바뀐 것은 아니다.
- View 정리: 광고 정보와 Tracker, 이미지의 갱신은 bindBanner로 모았고, 관찰자와 예약 작업 해제 및 진행 시간 초기화는 stopImpressionObservation으로 모아 detach와 destroy가 함께 사용한다. show의 결과 콜백 순서와 중첩 방지, 최종 해제의 의미는 유지한다.
- 설명 점검: BannerAdView의 클래스와 공개 API, 생명주기와 노출 검사 메서드를 한글로 설명했다. 로드 완료와 광고 표시 성공, 최초 노출 알림의 차이, A 유지와 B 교체, 리스너 참조와 늦은 결과 차단을 명시했다. BannerAdImpressionListener에도 등록 단위와 광고 ID별 한 번, 과거 이벤트 소급 없음과 콜백 정보 범위를 보강했다.
- 테스트와 검증: 기존 단위 테스트와 기기 테스트를 검토했다. 기기 테스트에 상위 View의 회전 및 배율 변환 제거 후 판정, 노출 판정 전 detach 후 재부착 시 시간 재측정을 추가했다. SDK 단위 27개와 API 34 ARM64 기기 25개가 모두 통과했고 Debug AAR와 APK 빌드, 두 모듈 Lint도 통과했다. 정확한 가림과 모든 회전 축, 메모리 누수 전체를 검증했다는 뜻은 아니다.
- 다음 판단: 사용자 코드 검토와 대표 시나리오 관찰을 마무리한다. 서버 전송과 재시도, 별도 관찰 객체 추출은 이번 정리에 추가하지 않았다. 새로운 정책이나 재사용 요구가 생기면 D-016의 경계를 다시 검토한다.

## D-019 — 중복 억제 기준을 서버 adId에서 SDK 로드로 변경

- 날짜: 2026-11-27
- 문제와 변경 근거: 사용자는 정상 재로드에서 서버가 같은 광고를 반환했다는 이유로 새 노출이 억제되는 문제를 지적하고 규칙 수정을 요청했다. 기존 구현과 D-015는 adId가 광고 제공 건마다 유일하다는 가정을 사용했다. 실제 모의 서버는 같은 PNG를 주면서 매번 새 UUID를 발급하므로 같은 이미지라는 이유만으로 차단되지는 않았다. 다만 같은 adId가 다시 반환되면 새 로드도 억제됐다. SDK의 로컬 판정이 서버 ID의 유일성에 의존하지 않도록 기존 계약을 변경한다.
- 재현: 실제 View에 같은 adId와 동일 PNG를 두 번 로드해 각각 show하는 기기 회귀 테스트를 먼저 추가했다. 변경 전에는 첫 알림은 받았지만 두 번째 알림을 기다리는 nextEvent에서 4초 시간 초과로 실패했다. 실패 위치는 새 테스트의 second 수신 부분이었다.
- 선택과 책임: 중복 키를 SDK에서 로드 완료된 광고의 식별값으로 바꿨다. 같은 소재의 재선정을 무효 노출로 판단하지 않는다. SDK는 한 로드에서 같은 노출 이벤트를 중복 생성하지 않고, 서버의 소재 선택과 빈도 정책, 제공 건의 유효성 확인과 최종 집계는 별도 계약으로 다룬다. 이 로컬 억제로 악의적인 반복 load나 부정 트래픽 전체를 차단했다고 주장하지 않는다.
- 구현: BannerAdView는 이미지 준비까지 끝나 PreparedBanner를 만들 때 View 내부의 증가하는 loadId를 발급하고 정보와 이미지에 연결한다. show는 그 값을 재사용한다. Tracker의 display(adInfo, loadId)는 loadId가 달라질 때만 연속 시간을 새로 재며, reportedLoadIds로 중복을 억제한다. 리스너 호출 전에 이력을 기록하는 순서는 유지한다. 이미 판정한 같은 loadId의 재등록과 재부착은 추가 알림을 만들지 않는다.
- A/B 경계: B의 load 시작이나 로드 완료는 View에 남은 A의 관찰을 바꾸지 않는다. B를 show한 시점부터 B의 시간을 새로 잰다. B가 A와 같은 adId를 가져도 새 loadId를 쓴다. 로드 실패와 취소로 B가 반영되지 않으면 A의 이력을 유지한다. HTTP 계층의 연결 복구와 show 반복은 새로운 로드 광고를 만들지 않는다.
- 공개 계약과 한계: BannerAdInfo는 기존 adId와 placementId를 그대로 전달하며 같은 값의 콜백이 서로 다른 로드에서 발생할 수 있다. 새 공개 필드와 서버 JSON 필드를 추가하지 않았다. loadId는 한 View 안에서만 유효하고 서버 제공 건 ID나 전역 이벤트 ID가 아니다. 서버 전송에서의 유효성 확인과 중복 수신 처리는 향후 별도 식별 계약이 필요하다. View 수명 중 이력이 누적되는 비용은 남으며 destroy에서 정리한다.
- 검증 결과: 시간 경계와 기존 로드의 중복 억제를 유지한 채 같은 adId의 새 로드가 각각 판정되고 이전 연속 시간을 이어받지 않는 단위 테스트를 추가했다. SDK 단위 29개(Tracker 11개)와 API 34 ARM64 기기 26개가 통과했다. Debug AAR와 APK 빌드, 두 모듈 Lint도 성공했다. Lint 오류는 0개이며 기존 SDK 버전 안내 경고 12개는 남는다. 사용자가 수정한 기존 테스트 이름과 주석은 보존하고 정책과 관련된 입력과 설명만 갱신했다.
- 적용 상태와 다음: 위 내용은 D-015와 D-016의 adId 기반 설명을 대체하는 현재 로컬 계약이다. README와 요구사항, 학습 문서 및 KDoc을 갱신했다. 사용자는 이후 이 변경의 커밋과 PR 본문 갱신을 요청했다. 원격 반영 상태는 프로젝트 맥락의 Git 기록을 따른다. 별도 관찰 객체 추출과 서버 트래킹을 이번 수정에 추가하지 않았다.

## D-020 — Tracker 반환값과 노출 콜백 호출의 표현 구분

- 날짜: 2026-11-27
- 문제: 사용자는 노출 설명과 테스트의 '알림'과 '알린다'가 실제 이벤트와 콜백 중 무엇을 뜻하는지 모호하다고 지적했다. 이 표현을 유지하려면 성공과 실패 콜백으로 구현하는 편이 낫다는 의견을 제시했다. 실제 코드는 Tracker가 BannerAdInfo 또는 null을 반환하고 View가 onImpression을 호출하는 두 단계인데, 설명과 테스트 제목에서 이를 섞어 사용했다.
- 수정: Tracker 단위 테스트는 광고 정보 반환과 null 반환을 명시하고, View 기기 테스트는 onImpression 콜백 호출과 미호출을 명시하도록 바꿨다. 기기 테스트의 콜백 수신 큐와 대기 헬퍼 이름, 실패 메시지도 구체화했다. Tracker의 reportedLoadIds는 조건 충족 판정 이력이라는 의미의 qualifiedLoadIds로 바꿨다. 동작과 공개 메서드 시그니처는 유지했다. KDoc과 샘플 UI, 로그, README와 요구사항의 현재 설명을 같은 기준으로 수정했다.
- 계약 검토: 호스트 앱에는 이미 BannerAdImpressionListener.onImpression 콜백을 제공한다. Tracker는 Android와 리스너 참조 없이 판정 결과를 반환한다. observe의 null은 아직 대기 중이거나 이미 판정한 로드, 미등록, 해제 상태를 포함하므로 실패와 같지 않다. 조건 미충족을 실패로 분류하면 숨김과 복귀에서 실패 이후 성공이 반복되는지 등의 새 계약을 정해야 한다.
- 판단: 현재 onImpression은 노출 조건을 최초 충족한 사실을 전달하는 콜백이다. 새로 성공과 실패 콜백을 추가하려면 판정 시도의 시작, 종료와 제한 시간 또는 취소 기준을 먼저 정해야 한다. 이번 수정에서는 표현을 실제 동작에 맞추고 기존 이벤트 콜백 계약을 유지했다. 로드와 show의 실패 콜백은 해당 명령의 실패를 계속 담당한다. 이번 의견을 실패 콜백 신설 요구사항으로 확정하지 않았다.
- 검증과 문서 관리: 단위 테스트 29개와 API 34 ARM64 기기 테스트 26개, Debug AAR 및 APK 빌드와 Lint가 통과했다. Lint 오류는 0개이며 기존 SDK 버전 안내 경고 12개는 남는다. 반복 적용할 표현 기준은 AGENTS.md에 추가했다. 현재 기능의 설명은 요구사항과 학습 문서에 반영했고, 과거 결정 기록은 당시의 표현과 판단 근거로 남겼다. 커밋과 PR 반영 상태는 프로젝트 맥락의 Git 기록을 따른다.
