# 광고 SDK의 문제와 요구사항

최종 내용 갱신일: 2026-11-27

운영 지침은 [AGENTS.md](../AGENTS.md)를 따른다. 관련 상태는 [프로젝트 맥락](project-context.md), 판단 근거는 [의사결정·실험 기록](decisions.md)을 참고한다.

## 프로젝트에서 해결할 문제

1. 광고 로드와 실제 광고 표시·노출을 구분해 준비만 된 광고를 노출로 기록하지 않는다.
2. 광고 없음·통신 실패·이미지 준비 실패를 구분해 연동 개발자가 원인을 이해하도록 한다.
3. 화면을 떠나 광고를 해제한 뒤 늦은 응답이 View·콜백을 갱신하는 상황을 방지한다.
4. 반복적인 화면 변화로 동일 광고 제공 건의 노출 이벤트가 중복 발생하는 상황을 통제한다.
5. SDK를 쓰는 개발자가 적은 연동 코드와 명확한 문서로 기능을 사용할 수 있도록 한다.
6. 수동 시연뿐 아니라 주요 시나리오를 테스트로 반복 검증할 수 있게 한다.
7. 선택적으로, 광고 표시 시점의 네트워크·이미지 준비 지연을 프리로드로 줄이고 효과와 비용을 비교한다.
8. 준비 완료·광고 표시 성공·첫 프레임·재생 시작·종료의 의미가 형식마다 다름을 이해하고, 오류·닫힘·완료를 같은 결과로 처리하지 않는다.
9. 앱 진입 단계에서는 광고 응답과 제한 시간·화면 전환이 경합해도 뒤늦은 광고 표시나 중복 진입이 발생하지 않도록 설계한다. 기본 배너 이후 검토할 확장 문제다.

기능 수보다 문제를 이해하고 개선한 근거를 중시한다. 각 작업에서 문제·영향받는 주체·현재 가설·대안·선택 이유·검증 방법·결과·한계·다음 질문을 연결한다. 실패하거나 채택하지 않은 대안도 의미 있는 관찰이 있으면 학습 근거로 남긴다.

## 최소 범위와 요구사항 초안

### 범위

- Kotlin Android용 SDK와 이를 사용하는 샘플 앱
- 이미지 배너 한 종류, 광고 지면 하나로 시작
- 광고 응답과 이벤트 수신을 제어할 수 있는 모의 서버 또는 테스트 서버
- 모의 서버는 광고 공급·이벤트 확인에 필요한 최소 역할만 담당
- 단위 테스트, 앱과 SDK를 연결한 통합 시나리오, 연동 문서
- SDK의 핵심 로직을 직접 구현한다. 기존 광고 SDK 호출 예제만으로 자체 SDK 구현 경험을 대체하지 않는다.

### 초기 프로젝트 구성 — 세팅 적용

- `:ad-sdk` Android Library와 `:sample-app` Android 앱을 구성하고, 앱이 SDK 모듈을 `implementation`으로 의존한다.
- 샘플 앱은 기존 앱 패키지 `io.github.junyoungwon.androidadsdkplayground`를 유지하며, SDK namespace는 `io.github.junyoungwon.adsdk`로 분리한다.
- JDK 17·Gradle 8.13·AGP 8.11.1·Kotlin 2.2.21, compileSdk 36·샘플 targetSdk 36을 사용한다. 두 모듈 minSdk 26과 바이트코드 11은 기존 템플릿을 유지한 초기 선택이며, SDK 제품의 영구 지원 범위 합의를 뜻하지 않는다.
- 기존 Views/XML 기반 샘플을 활용한다. 초기 세팅 이후 첫 배너의 로드·광고 표시 API와 모의 서버를 추가했다. 현재 계약은 아래 적용 항목을 따른다.
- 구현 의존성은 OkHttp 4.12.0·Coil 2.7.0·Coroutines 1.10.2·kotlinx.serialization JSON 1.9.0이다. 노출 판정은 아래 적용 계약을 따르며 클릭과 트래킹은 후속 범위다.
- 개발 환경·명령은 [README](../README.md), 선택 근거와 검증 범위는 [D-004](decisions.md#d-004--초기-프로젝트-세팅)를 따른다.

### 첫 배너에 적용한 계약

로드와 광고 표시를 분리하는 API는 사용자가 선택했다. 아래 재요청·해제·응답 규칙은 이번 구현에서 선택한 초기 정책이며, 광고 플랫폼 공통 표준이나 사용자와 개별 합의한 정책으로 표현하지 않는다.

| 항목 | 현재 동작 |
| --- | --- |
| 공개 API | `BannerAdView.load(BannerAdRequest, BannerAdListener)`, `show(BannerAdShowListener)`, `setImpressionListener(BannerAdImpressionListener?)`, `destroy()` |
| 스레드 | 공개 메서드는 메인 스레드에서 호출. 다른 스레드 호출은 `IllegalStateException`. 콜백도 메인 스레드에서 전달 |
| 로드 완료 | 광고 데이터 검증과 이미지 다운로드·디코딩이 끝난 뒤 `onLoaded()`. 이때 이미지와 광고 라벨은 아직 View에 반영하지 않음 |
| 광고 표시 | `show(listener)`가 마지막 load에서 로드 완료된 광고의 이미지를 View에 반영한 뒤 onShowSuccess(BannerAdInfo)를 전달. 반영할 수 없으면 onShowFailed(BannerAdShowError). show가 반환되기 전에 메인 스레드로 결과 하나를 전달. 반복 호출은 같은 광고로 매번 결과 알림 |
| 광고 표시와 노출 구분 | 광고 표시 성공 콜백은 View 이미지 반영 완료다. 부착·가시성·포그라운드·노출을 보장하거나 측정하지 않음 |
| 재요청 | 진행 요청을 취소하고 로드는 완료됐지만 아직 View에 반영하지 않은 광고를 버림. 표시 중인 이미지는 유지하며 가장 최근에 로드 완료된 광고를 show할 때 교체. 새 요청 실패 시에도 기존 광고 표시 유지. 이전 요청의 성공·실패 콜백은 전달하지 않음 |
| 결과 알림 | 교체·해제되지 않은 로드 시도는 준비 성공 또는 실패를 한 번 알림. 취소 자체는 실패 콜백으로 전달하지 않음 |
| 해제 | `destroy()`는 최종·멱등 동작. 진행 작업 취소, 광고 이미지와 로드 완료된 광고·소유한 로더 자원 정리, 늦은 결과·콜백 차단. 이후 `load()`는 무시하고 `show(listener)`는 DESTROYED 실패 알림 |
| 호스트 수명 | 호스트가 사용 종료 시 해제. 샘플은 `Activity.onDestroy()`에서 호출. 단순 detach·백그라운드 전환으로 해제·재로드하지 않음. 회전 시 이전 배너를 해제하고 새 화면에서 수동 로드 |
| 요청 한도 | 각 HTTP 호출 제한 시간 5초, 광고 JSON 최대 64 KiB. 광고 데이터·이미지 호출은 순차이므로 전체 로드 5초 제한을 뜻하지 않음 |
| 이미지 범위 | 래스터 이미지 디코딩은 Coil에 위임. 640×200 픽셀을 목표로 FIT 크기 조정, View에서도 비율을 유지. 샘플 영역은 높이 100dp. 메모리·디스크 광고 캐시는 사용하지 않음 |

공개 요청은 `placementId`와 완전한 HTTP(S) 응답 주소 `serverUrl`을 받는다. SDK가 `placementId` 쿼리 값을 설정하고 주소의 다른 쿼리는 유지한다. 모의 환경에서는 지면 하나인 `demo-banner`를 사용한다.

```http
GET /ads?placementId=demo-banner&scenario=normal
```

```json
{"adId":"서버 광고 ID","imageUrl":"http://127.0.0.1:8080/banner.png"}
```

- 최종 HTTP 200 응답에는 비어 있지 않은 문자열 `adId`, 절대 HTTP(S) 주소 `imageUrl`이 필요하다. 다른 필드는 무시한다.
- 204는 `NO_FILL`, 그 외 HTTP 상태는 `HTTP_ERROR`, JSON·필드 오류는 `INVALID_RESPONSE`다.
- 잘못된 요청 입력은 `INVALID_REQUEST`, 데이터 요청 통신 장애는 `NETWORK`, 제한 시간은 `TIMEOUT`으로 구분한다.
- 이미지의 HTTP·다운로드·디코딩 실패는 모두 이미지 준비 단계의 `IMAGE_LOAD`다. 로드 성공 알림과 광고 표시는 발생하지 않는다.
- SDK가 실패 후 `load()`를 자동 재호출하는 정책·이벤트 전송은 없다. HTTP 계층은 OkHttp의 기본 연결 복구를 허용하므로, 끊긴 풀 연결 등을 만났을 때 호출 제한 시간 안에서 GET이 재시도될 수 있다. 로드 콜백 한 번이 서버 요청 한 번을 보장하지 않는다. `adId`는 응답 검증과 광고 표시 성공 정보에 사용하며 아직 트래킹으로 전송하지 않는다.
- Python 표준 라이브러리 모의 서버는 로컬 루프백에서만 수신한다. Debug 샘플만 `127.0.0.1` HTTP를 허용하고 ADB reverse로 연결한다. SDK가 호스트의 네트워크 보안 정책을 완화하지 않는다.
- `normal`, `no-fill`, `http-error`, `invalid-response`, `image-failure`, `slow` 시나리오를 샘플에서 선택한다. 실행 절차는 [README](../README.md)를 따른다.
- 회전 실험용 샘플 UI는 `delayMs`로 광고 데이터 응답을 0~4000ms 지연시킨다. 미입력 시 0이며 범위를 벗어나거나 정수가 아니면 서버가 400을 반환한다. `slow`는 시간 초과 전용 8초 지연을 유지한다. 이 제어는 SDK의 지연·제한 시간 계약을 바꾸지 않는다.

### 재로드 중 기존 광고 유지와 광고 표시 결과 — 적용

사용자는 가장 최근에 로드 완료된 광고를 반영해야 광고 표시 성공으로 판단하는 방식을 선택했다. Boolean 대신 성공 시 광고 정보와 실패 시 원인을 전달하는 콜백을 도입했다. 광고 표시 상태 조회는 후속 기능으로 보류한다. 이전의 즉시 이미지 제거 정책과 반환 방식은 [D-010](decisions.md#d-010--재로드-중-기존-광고-유지의-검증-기준) 이후 [D-011](decisions.md#d-011--기존-광고-표시-유지와-광고-표시-결과-콜백)로 대체한다.

| 상황 | 동작 |
| --- | --- |
| A 광고 표시 중 B 로드 시작 | A 유지, 이전 작업 취소, 이전에 로드 완료된 광고 제거 |
| B 준비 중 show | LOADING 실패. A는 유지 |
| B 준비 완료, show 전 | A는 ImageView에서, B는 로드 완료된 광고로 세션에서 보관 |
| B 준비 후 show | A를 B로 교체한 뒤 B의 adId와 요청 placementId를 성공 콜백으로 전달 |
| B 준비 실패 후 show | LOAD_FAILED와 loadError 전달. A는 유지 |
| 한 번도 로드하지 않고 show | NOT_LOADED 실패 |
| destroy 후 show | DESTROYED 실패. 광고 표시 중인 이미지와 로드 완료된 광고는 해제 과정에서 정리 |

여기서 로드 완료된 광고는 마지막 load 요청으로 광고 데이터 검증과 이미지 다운로드 및 디코딩을 끝낸 광고다. show는 새 로드나 다운로드를 시작하지 않으며, 첫 광고 표시 이후에도 해당 광고를 보관한다. 새로운 load 없이 반복 호출하면 같은 광고 정보를 매번 성공 콜백으로 전달한다. 새 load가 시작되면 이전에 로드 완료된 광고는 무효화되므로, A가 계속 표시 중이어도 B 준비 전 또는 실패 후의 show는 실패한다.

광고 표시 리스너는 show(listener)에 전달하는 BannerAdShowListener이며, 이번 호출에서 광고 이미지를 View에 반영한 성공 또는 실패를 알린다. 실제 노출 조건 충족이나 노출 집계 결과를 알리는 리스너가 아니다.

SDK는 이 리스너를 이번 show 호출의 함수 인자로 사용하고, show가 반환되기 전에 콜백을 한 번 호출한다. BannerAdView나 BannerLoadSession의 멤버 변수에 리스너를 저장해 다음 호출이나 이후 이벤트에 사용하지 않는다. 따라서 다음 show에도 리스너를 전달해야 한다. 호스트가 같은 리스너 객체를 다시 전달하는 것은 가능하다. '저장하지 않는다'는 객체의 즉시 메모리 삭제를 뜻하지 않으며, 호스트가 별도로 참조하고 있다면 그 객체는 계속 존재할 수 있다. 비동기 load가 완료를 기다리는 동안 BannerAdListener를 참조할 수 있는 것과도 구분한다.

오류는 광고 표시 시점의 상태를 구분한다. LOAD_FAILED의 loadError에는 NO_FILL, TIMEOUT, IMAGE_LOAD 등 원래 로드 실패 원인을 담는다. 광고 표시 실패 콜백은 로드 실패 콜백을 대체하거나 기존 A가 사라졌음을 뜻하지 않는다. main 스레드 위반은 기존처럼 IllegalStateException이며 콜백 오류로 바꾸지 않는다. 호스트 콜백이 던진 예외를 다른 실패 콜백으로 다시 전달하지 않는다.

BannerAdInfo에는 adId와 placementId만 담는다. 이미지 객체와 내부 로더는 외부에 제공하지 않는다. adId는 서버 응답값이며 서로 다른 로드에서 같은 값이 올 수 있다. 로드 완료된 광고는 광고 정보와 Drawable을 함께 보관해 B를 반영하면서 A 정보를 전달하는 오류를 피한다. A와 B가 함께 유지되는 동안 메모리 비용이 늘 수 있으며, 참조 정리가 즉시 Bitmap 메모리 회수를 보장하지는 않는다.

### 전체 기능 기준 — 적용한 항목 외에는 제안

| 기능 | 제안된 최소 동작 | 검증할 핵심 |
| --- | --- | --- |
| 광고 요청 | 지면 ID로 모의 서버에 요청 | 필요한 정보 전달, 결과 구분 |
| 광고 데이터 처리 | 응답을 해석해 광고 표시 정보를 준비 | 정상 응답과 잘못된 응답 처리 |
| 이미지 준비 | 광고 이미지 다운로드와 디코딩까지 끝나면 로드 완료 알림 | 이미지 실패 시 성공 알림이 발생하지 않음 |
| 광고 표시 | `show()`로 SDK 배너 View에 준비한 이미지 반영 — 적용 | 준비 완료와 View 반영의 구분 |
| 노출 | 아래 프로젝트 조건을 충족하면 SDK에서 로드 완료된 광고마다 onImpression 콜백 최초 한 번 호출 — 적용 | 로드만 완료된 광고 제외, 중복 억제 |
| 클릭 | 클릭 이벤트 처리 후 광고 연결 URL 열기 | 클릭 이벤트와 이동 결과 구분 |
| 트래킹 | 모의 서버로 노출·클릭 전송 | 광고 제공 건과 이벤트 연결, 수신 확인 |
| 상태 알림 | 로드 성공·실패를 매체 앱에 전달 | 실패 원인과 콜백 계약의 명확성 |
| 해제 | 로드 취소·참조 정리·늦은 결과 무시 | 해제 후 화면·콜백 갱신 방지 |

onShowSuccess의 횟수는 노출 또는 과금 건수가 아니다. SDK의 노출 판정과 onImpression 콜백은 구현했지만 트래킹 전송과 서버 집계는 미구현이다.

### 배너 노출 판정 — 적용

feat/banner-impression-detection의 범위는 SDK가 현재 광고 표시 중인 광고의 조건 충족을 판정하고, 로드별 최초 노출 조건 충족 시 onImpression 콜백을 한 번 호출하는 것까지다. 서버 adId의 동일 여부로 서로 다른 로드를 합치지 않는다. 기존 show의 광고 표시 성공 계약은 유지한다. 사용자는 면적과 시간, 창 포커스 정책, View 단위 리스너 등록을 선택했다. 아래 중복 억제와 관찰 중단, 늦은 등록의 처리는 이를 구현하기 위한 세부 계약이다.

| 항목 | 현재 계약 |
| --- | --- |
| 대상 | show로 View에 반영한 광고. 로드만 완료된 광고는 제외 |
| 면적과 시간 | 광고 이미지가 차지하는 사각 영역의 50% 이상이 연속 1초 보일 때 판정. FIT_CENTER의 빈 여백은 제외 |
| View와 창 | 화면에 부착되고 View와 상위 View가 VISIBLE이며 alpha가 0보다 커야 함. 창도 VISIBLE이고 포커스가 있어야 함 |
| 관찰 중단 | 면적 미달, 숨김, 창 포커스 상실, detach 시 연속 시간을 초기화. 복귀하면 처음부터 측정 |
| 광고 교체 | B를 load하는 동안 A의 관찰 유지. B를 show하면 A의 대기 시간을 버리고 B의 시간을 새로 측정 |
| 반복 호출 | 같은 로드 광고의 show나 새 load 시작만으로 현재 광고의 진행 시간과 노출 이력을 초기화하지 않음 |
| 중복 범위 | SDK에서 한 번 로드 완료된 광고에 최초 한 번. 서버 adId와 이미지가 같아도 새로 로드 완료해 show하면 별도로 판정. 다른 View와 서버 집계의 중복 제거는 별도 범위 |
| 리스너 | setImpressionListener(listener)로 View에 등록. 광고 교체 후에도 유지. null로 해제하거나 새 리스너로 교체 가능 |
| 콜백 | BannerAdImpressionListener.onImpression(BannerAdInfo)를 메인 스레드로 전달. 조건 미충족은 대기이므로 실패 콜백 없음 |
| 등록 시점 | load/show 전에 등록 권장. 리스너가 없어도 판정 이력 유지. 뒤늦은 등록이나 리스너 교체로 과거 이벤트를 소급하거나 중복 전달하지 않음 |
| 콜백 순서 | show 결과 콜백 안에서는 노출 콜백을 전달하지 않음. 이후 현재 광고와 조건을 다시 확인. 판정 이력은 onImpression 호출 전에 기록해 재진입 중복 방지 |
| 해제 | detach는 관찰만 중지하고 광고와 이력 유지. destroy는 예약 작업, ViewTreeObserver 등록, 리스너 참조와 광고 정보를 정리하고 이후 onImpression 호출 차단. 해제 후 리스너 등록은 무시 |

adId는 서버 응답의 광고 식별값으로 전달하며, 중복 억제 키로 사용하지 않는다. SDK는 광고 데이터 검증과 이미지 준비를 끝내 로드 완료된 광고를 만들 때 View 내부의 증가하는 loadId를 발급하고, 광고 정보와 이미지에 연결한다. show는 이 값을 그대로 사용하며 새로 발급하지 않는다. 서버 adId와 이미지가 같아도 다른 로드 광고라면 다른 loadId를 사용하고, 새 광고를 show한 시점부터 연속 시간을 다시 측정한다. 새 load의 시작이나 성공 자체는 현재 광고의 판정 상태를 바꾸지 않는다.

loadId는 한 View 안의 판정용 식별값으로 서버의 광고 제공 건 ID나 전역 이벤트 ID가 아니다. 현재 모의 서버는 정상 응답마다 새 adId를 발급하지만 SDK가 그 유일성에 의존하지 않는다. BannerAdInfo의 adId와 placementId는 그대로 전달하므로 서로 다른 로드의 콜백 정보가 같을 수 있다. loadId는 외부에 제공하지 않으며 서버 전송 식별 계약은 후속 범위다. 이력은 View 수명 중 유지해 이미 판정한 loadId의 재등록을 차단하고 destroy에서 정리한다.

이 정책은 같은 로드에서 중복 이벤트가 발생하는 것을 억제한다. 같은 소재의 재선정 여부나 반복 로드의 사업상 허용 여부, 서버의 최종 유효 노출과 과금을 판정하지 않는다. 기존 adId 단위 정책의 변경 이유는 [D-019](decisions.md#d-019--중복-억제-기준을-서버-adid에서-sdk-로드로-변경)에 기록한다.

관찰은 화면 부착과 가시성, 창 상태, 스크롤, 레이아웃, 그리기 직전 이벤트에서 조건을 확인하고 남은 시간에 예약한 작업에서 다시 확인한다. 시간은 벽시계 변경의 영향을 받지 않는 uptimeMillis로 계산한다. Main 스레드가 지연되면 콜백도 늦어질 수 있으며 정확히 1초 시점의 전달을 보장하지 않는다.

Tracker.observe는 로드별 최초 조건 충족 시 BannerAdInfo를 반환하고, View가 그 반환값으로 등록된 리스너의 onImpression을 호출한다. Tracker의 반환값과 View의 콜백 호출은 서로 다른 검증 대상이다. null은 이번 observe 호출에서 새 판정 결과가 없다는 뜻이다. 아직 1초가 안 된 상태와 조건 미충족, 이미 판정한 로드, 광고 미등록과 최종 해제를 모두 포함하므로 실패 결과로 해석하지 않는다.

현재 onImpression은 노출 조건을 최초 충족한 사실을 전달하는 콜백이다. 관찰을 시작한 뒤 반드시 성공 또는 실패로 끝나는 요청 API가 아니다. 숨김과 포커스 상실은 연속 시간을 초기화하는 상태 변화이며, 다시 조건을 충족하면 이후에 콜백을 호출할 수 있다. 노출 실패 콜백을 추가하려면 판정 시도의 시작과 종료, 제한 시간이나 취소를 실패로 분류할지 먼저 계약으로 정해야 한다. 이번 용어 정리에서는 이를 추가하지 않는다.

1초는 최초 노출 조건 충족을 판정하기 위한 기준이다. 조건 충족 후의 총 가시 시간이나 최대 연속 시간을 집계하지 않으며, 노출 종료 콜백도 없다. onImpression의 BannerAdInfo는 adId와 placementId만 전달하고 시간값을 포함하지 않는다.

측정 한계:

- 면적과 시간은 이 프로젝트의 학습용 정책이다. 일반 노출의 공통 정의나 공인 조회 가능성 측정 구현으로 주장하지 않는다. 실제 사람이 광고를 봤음을 증명하지 않는다.
- getGlobalVisibleRect로 얻은 클리핑 영역과 이미지 사각형을 비교한다. 같은 창의 다른 View, 다른 앱 창에 의한 임의 가림이나 이미지의 투명 픽셀은 판정하지 않는다. SDK의 광고 라벨이 덮는 영역도 빼지 않는다.
- View 또는 상위 View의 회전과 배율 변환이 있으면 판정에서 제외한다. 복잡한 변환의 정확한 가시 면적 계산은 지원하지 않는다. alpha는 0 여부만 확인하며 반투명도에 비례한 면적 계산은 하지 않는다.
- 창 포커스는 프로젝트가 선택한 추가 조건이다. 포커스 없이 보이는 다중 창 광고도 이번에는 제외한다.
- 서버 전송, 전역 중복 제거, 유효성 확인과 과금은 구현하지 않았다. 클라이언트의 중복 콜백 억제만으로 악용 방지를 완성했다고 보지 않는다.

검증 시나리오:

| 상황 | 기대 결과 |
| --- | --- |
| 로드만 완료하거나 화면에 부착되지 않은 View에서 show | onImpression 콜백 호출 없음 |
| 이미지 면적 49%와 50%, 연속 시간 999ms와 1000ms | 기준 미달은 제외, 두 기준을 모두 충족하면 해당 광고 정보로 onImpression 콜백 한 번 호출 |
| 조건이 끊긴 후 다시 충족 | 이전 시간을 합산하지 않고 새 연속 시간으로 판단 |
| 같은 로드 광고의 show 반복, 재부착, 리스너 교체 | 노출 이력 유지, 추가 onImpression 호출 없음 |
| 같은 adId와 이미지를 새로 로드한 뒤 show | 별도 로드로 판정하며 다시 연속 1초를 충족하면 onImpression 콜백을 새로 호출 |
| A 광고 표시 중 B 로드와 실패 또는 B 로드 완료 후 show 전 | A가 판정 대상이며 A의 시간과 이력 유지 |
| B를 show해 교체 | A의 대기 시간 취소, B를 새로 관찰 |
| destroy 또는 노출 콜백에서 show와 destroy 호출 | 해제 후 콜백과 중복 콜백 호출 없음 |
| 리스너 없이 노출 조건 충족 후 등록 | 과거 이벤트 소급 없음. 이후 새 광고 이벤트는 현재 리스너에 전달 |

### 예외 상황과 책임

| 상황 | SDK 정책 초안 | 샘플 앱 정책 초안 |
| --- | --- | --- |
| 광고 없음·NoFill | 통신 실패와 구분해 전달 | 기존 광고가 있으면 유지, 없으면 빈 영역 처리 |
| 요청 실패·시간 초과 | 실패 원인을 구분해 전달 | 기존 광고가 있으면 유지하고 실패 원인 안내 |
| 이미지 준비 실패 | 로드 실패 전달, 준비하던 자원 정리 | 불완전한 광고를 표시하지 않음 |
| 로드 중 화면에서 광고 사용 종료 | 명시적 해제에 따라 취소하고 늦은 결과 무시 | 적절한 시점에 해제 호출 |
| 광고 표시 후 트래킹 전송 실패 | 로드·광고 표시 성공 상태와 별도로 처리 | 이용 흐름 유지 |

단순 백그라운드 전환과 광고 객체의 완전 해제는 구분한다. 광고 없음 결과는 네트워크 장애와 다른 정상적인 사업 결과다. 트래킹 실패는 이미 완료된 광고 로드를 실패로 되돌리는 사유가 아니다.

### 후속 검토·미정 사항

- 현재 표시 중인 광고 내용의 존재를 알려주는 조회 API 또는 상태 콜백은 사용자 선택으로 보류한다. show 결과를 상태 조회 대신 사용하지 않는다.
- 실제 연동 대상을 고려한 배너 크기·이미지 비율·지원 이미지 종류·최대 입력 크기 정책
- 이벤트 데이터 계약과 요청·소재·광고 제공 건 식별자 구조
- `show()` 이후 실제 렌더링·광고 표시 실패를 별도 알릴 필요가 있는지
- 현재 호스트 해제 계약의 사용성과 실제 화면 이동·회전·백그라운드 복귀 시나리오 추가 검증
- 전체 로드 제한 시간·이미지 단계 오류를 더 세분화할 필요가 있는지
- 다른 View와 프로세스에 걸친 노출 중복 제거, 서버 검증과 클릭 연타 처리
- URL 검증·이동 실패 처리
- 트래킹 전송의 수명, 실패 관찰 방식, 재시도 여부

## 권장 진행 순서와 완료 기준

1. **직무 중심 후속 학습·최소 요구사항 검토:** [학습 계획](learning-plan.md)에서 형식별 책임 차이를 이해하고, 첫 배너 구현에 필요한 정책만 확정한다. 후속 학습 전체가 끝날 때까지 기본 구현을 무기한 미루지 않는다.
2. **프로젝트 구성 — 세팅 완료:** `:ad-sdk`와 `:sample-app`을 연결하고 API 34 에뮬레이터에서 실행했다. 첫 광고 연동 검증은 다음 정상 흐름 단계에서 수행했다.
3. **정상 흐름 구현:** 요청 → 데이터·이미지 준비 → 로드 결과 알림 → 명시적 `show()`를 구현했다. API 34 기기에서 실제 HTTP·이미지 디코딩·광고 표시 분리를 확인했다.
4. **예외·해제 대응 — 기본 방어 구현:** 광고 없음·요청 실패·이미지 실패·교체·해제 후 늦은 결과를 다룬다. 실제 화면 생명주기 시나리오는 추가 검증 대상이다.
5. **트래킹:** 노출·클릭 발생 조건과 모의 서버 수신을 확인한다.
6. **검증·문서:** 단위 테스트와 핵심 연동 시나리오, README·API 문서·시연을 준비한다.
7. **선택 확장:** 기본 기능이 완료되면 프리로드·정적 스플래시·제한된 동영상 중 가용 시간과 설명할 문제를 기준으로 우선 한 가지를 고르는 방안을 제안한다. 선택은 아직 확정되지 않았다. R8 빌드 검증도 여유에 따라 수행한다.
8. **지원 자료 반영:** 완료한 일·선택 이유·검증 근거만 이력서·포트폴리오에 담는다.

테스트는 구현과 함께 작성해도 된다. 테스트 단계가 마지막이라는 뜻으로 해석하지 않는다.

검증할 최소 시나리오:

- 정상 응답과 이미지 준비 후 로드 완료·광고 표시
- 데이터 수신 후 이미지 준비 실패 시 로드 실패
- 광고 없음과 통신 실패의 구분
- 준비만 된 광고에서 노출 이벤트 미발생
- 정한 노출 조건 충족 시 동일 로드 건의 중복 이벤트 억제
- 해제 후 콜백·화면 갱신 방지
- 클릭 이벤트와 연결 페이지 동작
- 트래킹 전송 실패와 광고 표시 상태의 분리

모의 서버를 사용하는 통합 시나리오는 그 범위를 명시한다. 실제 광고망까지 검증한 E2E라고 과장하지 않는다.

초기 채용 준비 마일스톤에는 짧은 준비 기간이라는 제약이 있었다. 앞서 제안한 총 20~25시간과 약 7일의 구현·정리 등은 예시이며 확정 일정이 아니다. 실제 가용 시간에 맞춰 조정하고, 단기 결과물의 범위와 장기 경험 축적 목표를 구분한다. 일정이 부족하면 동시 구현 범위를 줄이되 문제·판단·검증 근거는 남긴다. 이후 범위는 [의사결정 기록](decisions.md)을 근거로 갱신한다.

## 탐구 작업과 제품 구현의 완료 기준

- 제품 구현: 정한 SDK 계약·실패 시나리오를 충족하는지 검증하고 한계를 명시한다.
- 탐구·비교 실험: 가설, 비교 조건, 관찰 결과, 해석과 한계를 남긴다. 예상한 결과가 나오지 않아도 가설을 재평가할 근거를 얻었다면 의미 있는 결과다.
- 설명만 수행한 시나리오와 실제 실행한 테스트·측정을 구분한다. 테스트 통과만으로 잘못 정의한 계약이 적합해지는 것은 아니다.
- 테스트·측정·사용자 시나리오에서 드러난 문제를 요구사항과 다음 실험에 반영한다.
