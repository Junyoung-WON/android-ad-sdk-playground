## 지원 대상과 프로젝트의 목적

### 지원 공고

- 회사: (주)와이즈버즈
- 직무: SDK 개발자 채용 연계형 인턴
- 공고: https://recruit-wisebirds.career.greetinghr.com/ko/o/243217
- 공고 원문은 사용자가 대화에 직접 제공했다. 아래 직무 이해는 그 원문을 기준으로 한다.

공고의 주요 업무:

1. 배너·카드·팝업·스플래시·동영상 등 광고 SDK 기능 개발 및 버그 수정
2. 광고 노출·클릭 트래킹 로직 개발 및 검증
3. 가이드 앱 개발
4. 단위·E2E 테스트 작성
5. 연동 가이드·API 문서 작성

주요 요구·우대 역량:

- 서버 API 연동, 자료구조·객체지향 기초, Git 사용

- 단위 테스트, Coroutines, 동영상·WebView, AI 코딩 도구 활용 경험 우대
- 주도적 개선, 품질 향상, 학습과 지식 공유를 강조

### 프로젝트 목적

광고 SDK가 매체 앱·앱 사용자·광고 시스템 사이에서 어떤 역할을 맡고 어떤 문제를 해결해야 하는지 이해한다. 실제 문제를 정의하고 가설·대안을 검토하며, 구현·관찰·검증과 개선을 반복해 스스로 설명할 수 있는 개발 경험과 판단 근거를 축적하는 것이 주된 목표다. 단순한 기능 완성, 학습 항목 이수, 채용용 결과물 제작만으로 목표를 달성했다고 보지 않는다.

와이즈버즈 지원은 초기 문제 선택과 단기 마일스톤의 맥락이다. 기존 Android 경험에 더해 다른 개발자가 사용하는 API·생명주기·이벤트 처리·자원 소유권·연동 경험을 고민한다. 채용 마감 이후에도 새로운 문제·관찰 결과에 따라 범위와 학습 계획을 갱신할 수 있다.

결과물은 GitHub 코드·README·샘플 앱을 우선한다. 완료한 내용과 근거를 이력서·포트폴리오에 반영하고, 여유가 있으면 블로그에 설계 판단과 검증 과정을 정리한다. 업로드·게시를 수행했다고 가정하지 않는다.

## 현재 진행 상태와 의사결정 구분

### 사용자가 동의한 방향

- 광고 기본 흐름을 먼저 학습하고 토이 광고 SDK를 구현한다.
- 준비 기간이 짧으므로 작은 범위를 완성하고 검증하는 데 집중한다.
- 배너 광고 중심의 기본 흐름, 샘플 앱, 테스트·문서라는 제안 방향을 바탕으로 진행한다.
- 프리로드는 기본 기능 구현 이후 시간과 여유가 있으면 추가하는 선택 기능으로 둔다.
- 사용자는 광고 전체 흐름을 충분히 이해했다고 밝혔다.
- 사용자는 SDK의 역할과 해결할 문제를 깊이 이해하고 개선 경험을 지속적으로 쌓는 것을 주된 목표로 명확히 했다.
- 작업·세션·커밋 종료 시 지침과 관련 문서를 점검·갱신하는 관리 방식을 요청했다.
- 사용자는 기능별 `feat/...` 브랜치에서 작업하고 원격 저장소의 PR을 통해 `main`에 병합하는 Git 작업 방식을 지정했다. 초기 세팅의 `main`만 먼저 업로드한 뒤 기능 브랜치 PR을 연다.
- 사용자는 첫 배너에서 `load()`로 준비하고 `show()`로 별도 표시하는 방식을 선택했다. 이미지 준비가 끝나야 로드 성공이며, 이 콜백은 실제 노출을 의미하지 않는다.

### 제안했지만 세부 확정은 남은 사항

- 단순한 화면 표시 조건으로 노출을 판단하고 동일 로드 건에서 한 번만 이벤트를 발생시킨다.
- [요구사항 문서](requirements.md)의 적용한 계약 외 노출·클릭·트래킹 등은 초안이다. 첫 요청·응답·재요청·해제 정책은 초기 구현 선택으로 기록했으며 개별 사용자 합의와 구분한다.
- 이번 문서 개선에서 추가한 다중 형식 학습·SDK 계약·테스트 행렬은 후속 학습·설계 제안이다. 동영상·스플래시 구현을 새로 합의한 것은 아니다.

### 완료한 학습과 아직 하지 않은 작업

- 광고 참여 주체, 광고 제공 흐름, RTB·미디에이션, 로드·노출·클릭·전환, 과금·수익 지표를 학습했다.
- 예외 상황과 최소 요구사항 초안을 설명했다.
- 기존 루트에 `:app` Android 템플릿이 생성돼 있음을 확인했다. 세팅 작업에서 이를 `:sample-app`으로 옮기고 `:ad-sdk` Android Library 의존성을 연결했다.
- 빌드 도구·샘플 UI 의존성과 README를 구성한 뒤, 이미지 배너의 요청·준비·표시·결과 알림·해제, 모의 서버와 테스트를 구현했다. 노출·클릭·트래킹·원격 저장소 업로드는 미수행이다.
- 동영상 재생 이벤트, 스플래시의 진입 제어, VAST·MRAID·OM SDK는 [학습 계획](learning-plan.md)에 후속 학습 주제로 정리했다. 사용자가 이를 이미 학습·구현했다고 기록하지 않는다.

## 결과물과 설명 원칙

학습·판단 근거는 [의사결정·실험 기록](decisions.md)에 남기며, 아래 결과물에도 연결한다.

결과물 우선순위:

1. 실행 가능한 코드와 샘플 앱
2. 실행·연동 가이드, 지원 범위·한계, 테스트 실행법이 담긴 README
3. 문제 → 선택한 정책·구조 → 검증 결과를 설명하는 짧은 시연과 기록
4. 이력서·포트폴리오 반영
5. 여유가 있으면 블로그 게시

SDK 구현과 광고 운영 경험을 구분한다. 이 프로젝트는 학습용 모의 광고 환경이며 실제 광고 서비스를 운영하거나 와이즈버즈 내부 SDK를 재현한 것으로 표현하지 않는다. 계획·구현·테스트 통과·실제 측정을 구분하고 완료한 사실만 성과로 쓴다.

사용자의 기존 Android 앱 경험은 원인 분석·테스트·생명주기·R8·CI 등의 근거로 연결할 수 있다. 다만 기존 앱 개발 경험을 이미 수행한 SDK 개발 경험으로 바꾸어 표현하지 않는다.

## 현재 구현 상태와 인계

- 사용자 요청 범위: 초기 세팅을 커밋한 뒤, 사용자가 생성·체크아웃한 `feat/banner-load-and-display`에서 첫 구현을 진행한다. 현재 브랜치와 기존 문서 변경을 확인하고 유지했다.
- 구성: `:ad-sdk` → AAR, `:sample-app` → APK, Python 표준 라이브러리 `mock-server/server.py`. SDK의 `load()`·`show()`·`destroy()`를 샘플에서 조작한다.
- 환경: JDK 17·Gradle 8.13·AGP 8.11.1·Kotlin 2.2.21·compileSdk 36·샘플 targetSdk 36·minSdk 26·바이트코드 11. 이유는 [D-004](decisions.md#d-004--초기-프로젝트-세팅), 재현 절차는 [README](../README.md)를 따른다.
- 실제 검증: Debug APK·AAR 빌드 성공, 두 모듈 Lint 오류 0개. SDK 검사에는 새 버전 안내 경고 12개, 샘플 검사에는 이슈가 없다. 최종 명령은 파일 감시 캐시를 사용하지 않도록 `--no-watch-fs`로 실행했다.
- 테스트: SDK 단위 테스트 16개와 API 34 ARM64 기기 통합 테스트 5개 통과. 기존 검증에 응답 대기 중 Activity 재생성·새 배너 재로드·지연값 복원 검증을 추가했다. 테스트 이름은 한글·밑줄로 정리했다. 실제 방향 전환·메모리 누수 전체 검증과는 구분한다.
- 수동 관찰: Python 모의 서버·ADB reverse로 정상 배너를 로드했다. 준비 완료 시 빈 영역, 표시 버튼 후 합성 이미지·광고 라벨을 캡처로 확인했다. 처음 발견한 연결 복구 문제와 재현·해결은 [D-005](decisions.md#d-005--첫-이미지-배너의-로드표시해제)에 기록했다.
- 미검증: 실제 광고망·노출·클릭·트래킹, 실제 화면 이동·회전·백그라운드 수명 전체, API 26·36 기기 실행, R8 활성화, 외부 앱의 AAR 소비. 모든 모의 응답 버튼을 수동으로 반복 시연한 것은 아니다.
- 문서 점검: 지침은 계약 상태를 요구사항으로 안내하도록 정정했고, README·요구사항·의사결정·이 문서를 갱신했다. 학습 계획에는 로드·표시 분리와 프리로드 완성의 차이를 반영했다. 광고 도메인 일반 사실의 변화는 없어 `ad-domain.md`는 유지했다.
- Git 기록: 초기 세팅은 `606cb25`이며 `main`은 이 커밋에 유지한다. 사용자 요청에 따라 현재 기능 브랜치의 변경을 SDK·단위 테스트·계약, 샘플·모의 서버·기기 테스트, 학습·판단·작업 지침의 세 단위로 커밋한다. 실제 해시는 Git 이력을 따른다. 원격 저장소는 아직 없고 사용자가 생성 후 링크를 전달할 예정이다. 푸시·PR 생성·병합은 미수행이다.
- 다음 단계: 원격 링크를 받은 뒤 초기 세팅의 `main`을 먼저 업로드하고 `feat/banner-load-and-display`를 푸시해 PR을 연다. 이번 로컬 커밋 작업에는 푸시·PR·병합·새 브랜치 생성을 포함하지 않는다. 후속 개선 후보는 `feat/retain-banner-on-reload`이며 PR 병합 후 시작한다. 착수 전 새 광고 준비 중/실패 후 show의 의미와 반환값을 정한다. 이미지 단계 취소·비가시 정책·프로세스 종료·노출·클릭·트래킹은 후속 범위다.
- 사용자 검토 상태: 사용자가 기대 동작과 코드 흐름 초안, 일부 테스트의 한글 주석을 작성한 뒤 실제 로딩 중 회전을 실험했다. 정상·회전 로그와 HTTP 취소 핸들러 로그를 제공했으며, 코드와 연결해 검토했다. UI 초기화·HTTP 취소 호출·서버 처리 중단·메모리 회수를 구분해 설명했다. 모든 수명 시나리오·최종 이해 확인까지 완료했다고 기록하지 않는다.
- 회전 실험 도구: 샘플에 0~4초 광고 데이터 응답 지연, 지연값 복원, 화면 ID·요청/결과/종료 로그를 추가했다. SDK 코드·호출 제한 시간·기존 광고 즉시 제거 정책은 바꾸지 않았다. 새 서버의 8081 포트에서 지연·입력 검증을 확인했으며, 기존 서버는 코드 수정 후 재시작해야 한다. [D-006](decisions.md#d-006--사용자-코드-검토와-회전-실험-지원)을 따른다.
- 검토 진행의 우려: 사용자는 흐름·객체 이해에 드는 시간과 지원 마감 전 학습·지원 자료 완성을 우려했다. 핵심 계약·수명 경로를 우선 검토하고 라이브러리 내부 탐구는 질문에 따라 확장하는 [검토 범위 조정](learning-plan.md#마감-전-검토-범위-조정--제안)을 제안했다. 검토 시간만으로 역량 부족을 단정하거나 완료 가능 일정을 보장하지 않는다.
- 마감·가용 시간 — 사용자 제공: 지원 마감은 2026-11-29(일) 23:59, 한국 시간 기준으로 관리한다. 개인 일정을 제외하고 프로젝트·학습·포트폴리오·이력서 등을 합쳐 약 36~40시간 사용할 수 있다. 추가 투입 가능성은 기본 일정의 전제로 삼지 않는다.
- 마감 계획 — 제안: 총 36시간을 현재 기능 직접 검토 6시간, 사용자 문제 개선 한 건 8시간, README·시연 3시간, 포트폴리오·이력서 10시간, 설명 연습 3시간, 예비·제출 점검 6시간으로 나눈다. 개선 후보는 사용자가 제안한 재로드 중 기존 광고 유지이며, 회전 검증 후 계약을 정한다. 11/26 기능 범위 확정, 11/28 제출 가능 자료 확보, 11/29 제출·오류 대응을 제안한다. 남는 최대 4시간은 예비로 두며 새로운 기능을 자동 추가하지 않는다. 범위·배분은 아직 사용자 합의나 확정 일정이 아니다. 이번 계획 정리에서 코드·테스트·커밋·병합은 수행하지 않았다.
- 지연 설정 문제 해결: 사용자 제보로 기본 8080의 구버전 서버가 delayMs를 무시하는 현상을 재현했다. 해당 프로세스를 최신 코드로 재시작한 뒤 3초 설정의 서버 응답 약 3.008초, 앱의 로드 성공까지 약 3.301초를 확인했다. 현재 기본 8080도 최신 서버이며 앱 코드는 바꾸지 않았다. 경위·검증은 [D-007](decisions.md#d-007--지연-설정을-무시하던-구버전-서버-프로세스)을 따른다.
- 회전 실험 검토: 사용자 추가 진단 로그를 보존한 채 HTTP 소스 단위 테스트 9개를 실행해 통과했다. 이번에는 제품 코드·정책 변경이나 새 기기 실험을 수행하지 않았다. 사용자 관찰의 근거·한계, 취소 핸들러의 역할, 회전 유지 설계 대안과 onDestroy 생략 상황은 [D-008](decisions.md#d-008--사용자의-로딩-중-회전-관찰과-취소-경로-검토)에 기록했다.
- 커밋 전 최종 검증(2026-11-24): SDK 단위 테스트 16개·Debug AAR/APK·두 모듈 Lint가 통과했다. 기기 테스트에서는 주석 처리된 onDestroy 해제 호출로 기존 화면 리스너 차단 검증이 실패해 호출을 복원했고, API 34 ARM64 기기 통합 테스트 5개·샘플 Lint를 다시 실행해 통과했다. SDK 버전 안내 경고 12개는 남는다. 원인·분할 기준·PR 전환은 [D-009](decisions.md#d-009--기능-커밋-분리와-원격-pr-작업-방식)을 따른다.
