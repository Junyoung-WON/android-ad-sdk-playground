### 프로젝트 목적

광고 SDK가 매체 앱·앱 사용자·광고 시스템 사이에서 어떤 역할을 맡고 어떤 문제를 해결해야 하는지 이해한다. 실제 문제를 정의하고 가설·대안을 검토하며, 구현·관찰·검증과 개선을 반복해 스스로 설명할 수 있는 개발 경험과 판단 근거를 축적하는 것이 주된 목표다. 단순한 기능 완성, 학습 항목 이수, 채용용 결과물 제작만으로 목표를 달성했다고 보지 않는다.

와이즈버즈 지원은 초기 문제 선택과 단기 마일스톤의 맥락이다. 기존 Android 경험에 더해 다른 개발자가 사용하는 API·생명주기·이벤트 처리·자원 소유권·연동 경험을 고민한다. 채용 마감 이후에도 새로운 문제·관찰 결과에 따라 범위와 학습 계획을 갱신할 수 있다.

결과물은 GitHub 코드·README·샘플 앱을 우선한다. 완료한 내용과 근거를 이력서·포트폴리오에 반영하고, 여유가 있으면 블로그에 설계 판단과 검증 과정을 정리한다. 업로드·게시를 수행했다고 가정하지 않는다.

## 현재 진행 상태와 의사결정 구분

### 사용자가 동의한 방향

- 광고 기본 흐름을 먼저 학습하고 토이 광고 SDK를 구현한다.
- 준비 기간이 짧으므로 작은 범위를 완성하고 검증하는 데 집중한다.
- 배너 광고 중심의 기본 흐름, 샘플 앱, 테스트·문서라는 제안 방향을 바탕으로 진행한다.
- 프리로드는 기본 기능 구현 이후 시간과 여유가 있으면 추가하는 선택 기능으로 둔다.
- 사용자는 광고 전체 흐름을 충분히 이해했다고 밝혔다.
- 사용자는 SDK의 역할과 해결할 문제를 깊이 이해하고 개선 경험을 지속적으로 쌓는 것을 주된 목표로 명확히 했다.
- 작업·세션·커밋 종료 시 지침과 관련 문서를 점검·갱신하는 관리 방식을 요청했다.
- 사용자는 기능별 `feat/...` 브랜치에서 작업하고 원격 저장소의 PR을 통해 `main`에 병합하는 Git 작업 방식을 지정했다. 초기 세팅의 `main`만 먼저 업로드한 뒤 기능 브랜치 PR을 연다.
- 사용자는 첫 배너에서 load()로 준비하고 show()로 별도 광고 표시하는 방식을 선택했다. 이미지 준비가 끝나야 로드 성공이며, 이 콜백은 실제 노출을 의미하지 않는다. 노출 판정은 이미지 면적 50% 이상 연속 1초와 창 포커스를 조건으로 하며 View 단위 리스너 등록을 선택했다.

### 제안했지만 세부 확정은 남은 사항

- [요구사항 문서](requirements.md)의 적용한 계약 외 클릭과 트래킹 등은 초안이다. 첫 요청·응답·재요청·해제 정책은 초기 구현 선택으로 기록했으며 개별 사용자 합의와 구분한다.
- 이번 문서 개선에서 추가한 다중 형식 학습·SDK 계약·테스트 행렬은 후속 학습·설계 제안이다. 동영상·스플래시 구현을 새로 합의한 것은 아니다.

### 완료한 학습과 아직 하지 않은 작업

- 광고 참여 주체, 광고 제공 흐름, RTB·미디에이션, 로드·노출·클릭·전환, 과금·수익 지표를 학습했다.
- 예외 상황과 최소 요구사항 초안을 설명했다.
- 기존 루트에 `:app` Android 템플릿이 생성돼 있음을 확인했다. 세팅 작업에서 이를 `:sample-app`으로 옮기고 `:ad-sdk` Android Library 의존성을 연결했다.
- 빌드 도구·샘플 UI 의존성과 README를 구성한 뒤, 이미지 배너의 요청·로드 준비·광고 표시·결과 알림·해제, 모의 서버와 테스트를 구현했다. 첫 기능 당시 노출과 클릭, 트래킹은 미구현이었다. 첫 기능은 원격 PR #1을 통해 main에 병합했다. 재로드 중 기존 광고 유지와 광고 표시 콜백도 PR #2로 병합했다. 현재 브랜치에서는 노출 조건 판정과 View 단위 콜백을 구현하고 자동 테스트로 확인했다. 서버 트래킹과 클릭은 미구현이다.
- 동영상 재생 이벤트, 스플래시의 진입 제어, VAST·MRAID·OM SDK는 [학습 계획](learning-plan.md)에 후속 학습 주제로 정리했다. 사용자가 이를 이미 학습·구현했다고 기록하지 않는다.

## 결과물과 설명 원칙

학습·판단 근거는 [의사결정·실험 기록](decisions.md)에 남기며, 아래 결과물에도 연결한다.

결과물 우선순위:

1. 실행 가능한 코드와 샘플 앱
2. 실행·연동 가이드, 지원 범위·한계, 테스트 실행법이 담긴 README
3. 문제 → 선택한 정책·구조 → 검증 결과를 설명하는 짧은 시연과 기록
4. 이력서·포트폴리오 반영
5. 여유가 있으면 블로그 게시

SDK 구현과 광고 운영 경험을 구분한다. 이 프로젝트는 학습용 모의 광고 환경이며 실제 광고 서비스를 운영하거나 와이즈버즈 내부 SDK를 재현한 것으로 표현하지 않는다. 계획·구현·테스트 통과·실제 측정을 구분하고 완료한 사실만 성과로 쓴다.

사용자의 기존 Android 앱 경험은 원인 분석·테스트·생명주기·R8·CI 등의 근거로 연결할 수 있다. 다만 기존 앱 개발 경험을 이미 수행한 SDK 개발 경험으로 바꾸어 표현하지 않는다.

## 현재 구현 상태와 인계

- 사용자 요청 범위: PR #2 병합 이후 feat/banner-impression-detection에서 노출 계약을 검토했다. 사용자가 면적과 시간, 창 포커스 정책에 이어 View 단위 리스너를 선택해 구현과 검증을 진행했다. 시작 커밋은 a2f6e45다.
- 구성: `:ad-sdk` → AAR, `:sample-app` → APK, Python 표준 라이브러리 `mock-server/server.py`. SDK의 load(), show(listener), destroy()를 샘플에서 조작한다. setImpressionListener로 등록한 onImpression 콜백 수신 횟수와 광고 ID를 보여주고 배너 숨기기와 다시 보이기를 지원한다.
- 환경: JDK 17·Gradle 8.13·AGP 8.11.1·Kotlin 2.2.21·compileSdk 36·샘플 targetSdk 36·minSdk 26·바이트코드 11. 이유는 [D-004](decisions.md#d-004--초기-프로젝트-세팅), 재현 절차는 [README](../README.md)를 따른다.
- 실제 검증(2026-11-27): Debug APK·AAR 빌드 성공, 두 모듈 Lint 오류 0개. SDK 버전 안내 경고 12개는 남는다. 최종 단위·기기 테스트와 Lint는 --no-watch-fs로 실행했다.
- 테스트(2026-11-27): SDK 단위 29개와 API 34 ARM64 기기 통합 26개가 모두 통과했다. 기존 로드와 광고 교체 계약에 더해 연속 시간 경계, 중단과 교체, 동일 adId 재로드와 기존 로드의 중복 억제, 면적 49%와 50%, FIT_CENTER 여백, 스크롤, 미부착, alpha 0, 숨김과 창 포커스, 리스너 교체와 늦은 등록, 해제와 콜백 재진입을 검증했다. 픽셀 단위 가림과 메모리 누수 전체 검증은 아니다.
- 수동 관찰: 2026-11-26 에이전트가 API 34 샘플에서 노출 알림 1회와 반복 show, 숨김 후 복귀 시 1회 유지를 확인했다. 사용자 직접 관찰과는 구분한다. 이전에는 Python 모의 서버·ADB reverse로 정상 배너를 로드했다. 준비 완료 시 빈 영역, 광고 표시 버튼 후 합성 이미지·광고 라벨을 캡처로 확인했다. 처음 발견한 연결 복구 문제와 재현·해결은 [D-005](decisions.md#d-005--첫-이미지-배너의-로드광고-표시해제)에 기록했다.
- 미검증: 실제 광고망, 공인 노출 측정, 클릭과 서버 트래킹, 실제 화면 이동·회전·백그라운드 수명 전체, API 26·36 기기 실행, R8 활성화, 외부 앱의 AAR 소비. 모든 모의 응답 버튼을 수동으로 반복 시연한 것은 아니다.
- 문서 점검: AGENTS.md의 반복 지침은 변경할 필요가 없었다. 요구사항에 적용한 노출 계약과 한계를 반영하고 README 연동 예시와 직접 관찰 절차, D-015의 선택 이유와 검증 결과, 학습 계획의 코드 검토 순서를 갱신했다. ad-domain.md에는 조회 가능성과 일반 노출의 차이, Android 사각 영역과 창 포커스의 의미를 공식 자료와 함께 정리했다.
- Git 기록: [PR #2](https://github.com/Junyoung-WON/android-ad-sdk-playground/pull/2)는 사용자가 병합했다. 현재 feat/banner-impression-detection은 a2f6e45에서 시작했다. 사용자 요청으로 SDK와 계약, 샘플과 기기 테스트를 각각 커밋해 푸시하고 [PR #3](https://github.com/Junyoung-WON/android-ad-sdk-playground/pull/3)을 생성했다. 정책 선택과 학습, 책임 검토 기록까지 세 커밋으로 반영했다. 이후 사용자가 요청한 중복 기준 수정은 로컬 미커밋 상태이며, 원격 PR 본문과 코드는 아직 adId 기준이다. main은 유지하며 이번 PR의 병합은 수행하지 않았다.
- 다음 단계 — 제안: SDK 로드 단위로 변경한 현재 로컬 계약과 코드 흐름을 검토한다. 커밋과 푸시 시 [PR #3](https://github.com/Junyoung-WON/android-ad-sdk-playground/pull/3)의 이전 adId 기준 본문과 코드 링크도 함께 갱신해야 한다. 사용자의 대표 시나리오 관찰은 자동 테스트와 구분한다. 병합 여부는 별도로 결정한다. 지원 자료를 확보한 뒤 여유에 따라 노출 서버 전송과 중복 수신 처리 계약을 검토한다. 별도 관찰 객체 추출은 보류했으며 필요한 분리는 실제 변경 근거를 보고 판단한다. 새 기능 착수와 병합은 이번 커밋 및 PR 요청에 포함하지 않는다.
- 사용자 검토 상태: 사용자가 기대 동작과 코드 흐름 초안, 일부 테스트의 한글 주석을 작성한 뒤 실제 로딩 중 회전을 실험했다. 정상·회전 로그와 HTTP 취소 핸들러 로그를 제공했으며, 코드와 연결해 검토했다. UI 초기화·HTTP 취소 호출·서버 처리 중단·메모리 회수를 구분해 설명했다. 모든 수명 시나리오·최종 이해 확인까지 완료했다고 기록하지 않는다.
- 회전 실험 도구: 샘플에 0~4초 광고 데이터 응답 지연, 지연값 복원, 화면 ID·요청/결과/종료 로그를 추가했다. SDK 코드·호출 제한 시간·기존 광고 즉시 제거 정책은 바꾸지 않았다. 새 서버의 8081 포트에서 지연·입력 검증을 확인했으며, 기존 서버는 코드 수정 후 재시작해야 한다. [D-006](decisions.md#d-006--사용자-코드-검토와-회전-실험-지원)을 따른다.
