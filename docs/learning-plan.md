## 선택 기능: 프리로드

사용자는 표시 지연을 줄이는 프리로드에 관심을 보였고, 기본 기능 이후 여유가 있을 때 추가하기로 했다. 필수 범위를 밀어내며 먼저 구현하지 않는다.

### 학습한 효과와 한계

- 광고 요청과 자원 준비를 표시 시점보다 앞당겨 대기 시간을 줄인다.
- JSON만 미리 받으면 이미지 로드 지연은 남을 수 있다. 무엇을 준비해야 완료인지 정의해야 한다.
- 렌더링 시간까지 0이 되는 것은 아니다.
- 사용자가 로드 완료 전에 이탈하는 상황을 줄여 노출 기회를 확보할 수 있지만, 노출·수익 증가를 보장하지는 않는다.
- 광고 없음·입찰 불참 문제를 해결하지 못한다.
- 사용하지 않는 광고를 미리 준비하면 네트워크·메모리·준비 작업을 낭비할 수 있다.

### 최소 구현 제안

- 광고 지면 하나·준비된 광고 한 건·메모리 보관으로 제한한다.
- 로드와 표시를 분리하고, 준비 중이거나 유효한 광고가 있으면 중복 준비 요청을 막는다.
- Activity·View를 장기 캐시하는 대신 화면과 분리한 광고 데이터·이미지 자원 보관을 우선 검토한다.
- 유효 시간, 소비·폐기 기준, 취소 후 늦은 응답을 반영하지 않는 정책을 정한다.
- 준비된 광고가 없거나 만료된 경우 일반 로드로 전환하는 방식을 제안했다.
- 한 번의 표시에 사용한 뒤 캐시에서 제거하는 정책을 제안했으나, 모든 광고 형식의 공통 규칙으로 일반화하지 않는다.
- 다른 SDK의 만료 시간은 그 제품의 정책이다. 예를 들어 특정 Google 광고 형식의 1시간을 우리 배너의 공통 표준으로 복사하지 않는다.
- 여러 지면·여러 건 캐시, 자동 보충·재시도, 디스크 보관은 기본 범위에 넣지 않는다.

### 검증

- 동일 광고·응답·이미지·지연 조건에서 프리로드 유무에 따른 화면 진입 → 표시 완료 시간을 비교한다.
- 준비 시간과 네트워크 작업이 앞선 시점으로 이동했다는 점을 함께 기록한다.
- 준비 완료 전 진입과 완료 후 진입을 구분한다.
- 미표시 광고의 노출 미발생, 만료·사용 후 재사용 방지, 취소·중복 호출을 검증한다.
- 실제 측정하지 않은 단축 수치나 노출·수익 증가를 이력서에 쓰지 않는다.

## 구현하며 학습할 개념

학습은 광고 공급·거래의 전체 흐름에서, 앱 안의 광고 경험과 SDK의 책임으로 초점을 옮긴다. 아래 형식별 주제는 후속 학습 대상이며 기본 구현의 자동 확장을 의미하지 않는다.

| 개념 | 이번 프로젝트와의 연결 |
| --- | --- |
| Android Library와 AAR | 다른 앱에서 사용할 수 있는 SDK 구성·연동 |
| 공개 API와 내부 구현 분리 | 사용자에게 필요한 기능만 노출하고 연동 계약 정의 |
| Context·View·생명주기 | 화면에 종속된 자원과 SDK 작업의 수명 관리 |
| Coroutines·취소·동시성 | 비동기 로드, 중복 호출, 해제 후 늦은 결과 제어 |
| 상태 모델 | 요청·준비·표시·해제, 필요시 재생·전체 화면 상태와 트래킹 상태 구분 |
| HTTP·직렬화·이미지 로드 | 광고 공급 과정과 실패 원인 분리 |
| 이벤트 식별·중복 억제 | 노출·클릭의 의미와 발생 단위 정의 |
| 의존성 주입·대역 | 서버·이미지 준비·시간·이벤트 전송을 통제하는 테스트 |
| 단위·통합·UI 테스트 | 정책 로직과 실제 연동 흐름을 각각 검증 |
| 문서와 샘플 앱 | SDK를 처음 쓰는 개발자의 연동 경험 개선 |
| R8 호환성 | 여유가 있으면 R8 활성화 샘플 앱에서 실행 검증 |
| 캐시·만료·소비·측정 | 프리로드를 추가할 때 학습 |
| 표시 위치·표현 방식·소재 종류 | 배너·카드·팝업·스플래시·동영상을 서로 배타적인 타입으로 단정하지 않음 |
| 재생 상태와 이벤트 | 준비·버퍼링·첫 프레임·재생·완료·오류의 구분을 후속 학습 |
| 앱 진입 제어와 종료 계약 | 정적 스플래시를 검토할 때 늦은 응답·제한 시간·중복 종료 경합 분석 |
| 관찰 가능성 | 요청·표시 건을 연결한 이벤트 순서와 실패 원인 확인 |

필요한 경우에만 소비자 keep 규칙을 추가하고 범위를 좁힌다. 프로젝트를 복잡하게 만들기 위한 프레임워크·모듈 분할·추상화는 피한다.

### 1. 광고 형식을 바라보는 관점

공고의 형식 이름은 표시 위치·표현·타이밍·소재를 함께 나열한 것일 수 있다. 예를 들어 동영상이 카드나 전체 화면 안에 들어갈 수 있다. 실제 조합과 제품 정의는 별도로 확인한다.

| 형식·관점 | 학습할 문제와 질문 | 토이 프로젝트 적용 |
| --- | --- | --- |
| 배너 | 크기·비율·레이아웃, 화면 밖 이동, 재부착·재사용, 노출 단위 | 기본 구현. 정교한 가림 판정은 제한 명시 |
| 카드·네이티브 형태 | 앱이 구성하는 UI와 SDK의 계측 책임, 클릭 영역, 광고 표시·필수 자산, 목록 재활용 시 리스너·광고 바인딩 | 학습·시나리오 검토. 공고의 카드가 Native Ad라는 보장은 없음 |
| 팝업·전체 화면 | 중복 표시, 닫기·뒤로 가기, 표시 실패, 창·Activity 수명, 클릭 후 복귀 | 종료 이유와 표시 권한을 후속 학습 |
| 스플래시·앱 진입 시 광고 | 준비 기한, 광고 없음·실패 시 콘텐츠 진입, 늦게 도착한 광고, 복귀 시 재표시, 스킵·종료 경합 | 정적 이미지로 한정한 확장 후보 |
| 동영상 소재 | 첫 프레임, 버퍼링·재생 상태, 비율, 음소거·오디오 포커스, 배경 전환·복귀, 진행률 계측, 플레이어 해제 | 우선 학습. 구현은 제한된 확장 후보 |

### 2. 모든 형식에서 검토할 SDK 계약

다음은 제품 설계 시 명시할 항목이다. 정답을 먼저 고정하기보다 최소 범위에 맞는 정책과 이유를 정한다.

1. **준비·표시 계약:** 로드 성공이 무엇까지 보장하는지, 표시 가능 여부와 표시 실패를 어떻게 알리는지 정의한다. 이미지 전체 준비 정책을 동영상 전체 다운로드 정책으로 확대하지 않는다.
2. **상태별 허용 동작:** 준비 중 재요청, 표시 중 다시 표시, 해제 후 호출의 동작을 정한다. 하나의 `isLoaded`로 모든 상태를 대표하지 않는다.
3. **요청 경합:** 이전 요청의 늦은 결과가 새 요청을 덮어쓰지 않게 한다. 요청 세대·작업 식별 또는 취소 등을 필요에 맞게 선택한다.
4. **콜백:** 같은 로드 시도의 성공·실패가 중복 전달되지 않도록 정의한다. 닫힘·완료·오류·표시 기회 포기는 의미가 다르며, 정해진 종료 결과를 중복 전달하지 않는 정책을 검토한다. 해제 시 콜백을 없애는 계약과 앱 진입 완료 계약을 혼동하지 않는다.
5. **스레드·소유권:** 공개 API의 호출 스레드, UI 변경·콜백 스레드, SDK 작업·View·타이머·플레이어의 소유자와 해제 시점을 문서화한다. 메인 스레드에서 네트워크·이미지 디코딩 등 무거운 일을 수행하지 않는다.
6. **앱 흐름 보호:** 광고 없음·오류·기한 초과가 콘텐츠 이용을 무기한 막지 않도록 정책을 정한다. 광고를 표시할 시점의 선택과 실제 앱 내비게이션은 매체 앱의 책임으로 유지한다.
7. **이벤트 의미:** 로드·표시·노출·재생·완료·클릭·이동 결과를 구분한다. 내부 디버그 이벤트, 호스트 콜백, 서버 트래킹을 분리하고 식별자로 연결한다.
8. **확장 경계:** 실제 공통 동작만 공유한다. 하나의 거대한 광고 클래스에 영상·스플래시의 모든 조건을 넣거나, 반대로 아직 쓰지 않는 형식별 인터페이스를 미리 만들지 않는다.

### 3. 동영상에서 추가로 학습할 것

- `STATE_READY`는 실제 재생·첫 프레임·노출과 같지 않다. Media3에서는 재생 의도와 재생 억제 상태도 실제 재생 여부에 영향을 준다.
- 준비 완료, 첫 프레임 렌더링, 실제 재생, 버퍼링, 일시정지, 완료, 오류를 구분한다. 한 상태 신호를 모든 광고 이벤트로 복사하지 않는다.
- 25%·50%·75%·완료 같은 진행 이벤트를 다룬다면 기준을 정의한다. 단순 벽시계 경과 시간을 시청 시간으로 간주하지 않고, 버퍼링·정지·탐색·재생 반복의 영향을 검토한다.
- 첫 시작과 재개, 건너뛰기·사용자 닫기와 끝까지 재생 완료를 구분한다. 중도 오류나 해제를 정상 완료로 계측하지 않는다.
- 앱이 보이지 않거나 카드가 화면 밖으로 이동했을 때 영상·오디오를 어떻게 다룰지 정한다. 복귀 시 재개 여부와 오디오 포커스·음소거 정책은 별도다.
- 플레이어·Surface·리스너·진행률 관찰 작업의 수명과 해제를 다룬다. 목록의 여러 광고가 동시에 플레이어를 점유하는 문제를 이해한다.
- 플레이어 라이브러리의 신호를 광고 도메인 이벤트로 옮기는 역할을 구분한다. 검증된 플레이어·이미지 라이브러리를 사용하는 것은 가능하며 디코더를 직접 만드는 것이 목적이 아니다.
- 확장 구현을 선택한다면 고정 MP4 한 건, 단일 표시 위치, 기본 재생·오류·해제로 제한하고 나머지는 후속 항목으로 둔다. 이는 구현 확정이 아니다.

### 4. 스플래시에서 추가로 학습할 것

- Android 시스템 시작 화면, 앱의 로딩 화면, 그 위에 표시하는 광고의 수명은 구분한다. 공고의 스플래시가 어떤 제품 동작인지 확인하기 전에는 특정 SDK 형식을 그대로 대입하지 않는다.
- 콜드 스타트와 웜 스타트·포그라운드 복귀의 차이, 광고 표시 자격이 있는 Activity·화면을 학습한다.
- 광고 로드 제한 시간, 표시 가능 기한, 표시 후 노출 유지·스킵 가능 시간, 캐시 만료는 서로 다른 시간이다.
- 앱 콘텐츠 준비 완료·광고 로드 완료·대기 기한·사용자 스킵 등이 경합할 때 결과를 정한다. ‘기한 초과 → 콘텐츠 진입 → 늦은 응답 → 갑작스러운 광고 표시’를 대표적인 금지 시나리오로 제안한다.
- 콘텐츠 진입은 호스트 앱이 수행한다. SDK가 종료·건너뜀·실패 등을 알리는 방식과 호스트가 진입을 중복 수행하지 않는 방식을 각각 정의한다.
- 카운트다운이 있다면 의미를 정하고, 대기 기한은 단조 시간 기준과 제어 가능한 시계로 검증하는 방식을 검토한다. 화면의 숫자 감소만으로 타이밍 정확성을 판단하지 않는다.
- 광고 클릭으로 외부 앱을 다녀온 복귀가 새 스플래시 광고의 트리거가 되는 문제, 회전·화면 재생성·전체 화면 중복 표시를 검토한다.
- 확장 구현은 정적 이미지·명시적인 최대 대기·종료 결과 한 번 전달 정도로 한정할 수 있다. 대기 시간 수치는 아직 정하지 않았다.

### 5. 형식과 상태를 조합한 검증

고정 개수의 테스트를 목표로 삼기보다 사용자 동작·플랫폼 이벤트·비동기 결과가 만나는 지점을 선택한다. 기본 배너의 실제 테스트와 미구현 형식의 검토 시나리오를 구분한다.

| 상황 | 확인할 성질 | 적용 |
| --- | --- | --- |
| 첫 요청 지연 중 두 번째 요청이 완료됨 | 늦은 첫 결과가 현재 광고·콜백을 덮어쓰지 않음 | 공통 계약 확정 후 기본 범위 |
| 노출 후 스크롤·재부착·복귀 | 정한 동일 표시 건 기준으로 중복 계측되지 않음 | 배너·카드 |
| 해제와 로드 완료가 경합 | 해제된 View·콜백을 갱신하지 않음 | 기본 범위 |
| 제한 시간 직전·정각·직후에 광고 도착 | 뒤늦은 표시와 중복 콘텐츠 진입이 없음 | 스플래시 확장 시 |
| 로드됐지만 재생 전 정지·버퍼링 | 시작·진행·완료 이벤트를 허위 발생시키지 않음 | 동영상 확장 시 |
| 재생 도중 화면 종료·오류 | 정상 완료로 기록하지 않고 자원을 정리함 | 동영상 확장 시 |
| 외부 연결 페이지에서 복귀 | 의도하지 않은 전체 화면 광고 재표시가 없음 | 전체 화면 확장 시 |

실제 시간 지연을 기다리는 테스트 대신 필요한 경우 시계·디스패처·서버 응답·플레이어 신호를 제어한다. 실제 기기·에뮬레이터에서는 배치·클릭·생명주기 등 통합 동작을 별도로 확인한다.

### 6. 표준과 운영 관점의 후속 학습

- **VAST:** 동영상 광고를 전달하는 XML 응답과 플레이어 동작·트래킹의 계약을 이해한다. MP4 URL을 직접 재생하는 것만으로 VAST 지원이라고 표현하지 않는다.
- **MRAID:** 앱 내 리치 미디어 소재와 네이티브 컨테이너의 상호작용을 위한 인터페이스를 이해한다. WebView 사용 자체가 MRAID 구현은 아니다.
- **OM SDK:** 외부 측정 사업자의 조회 가능성·검증 측정을 돕는 역할을 이해한다. 자체 가시 영역 계산을 표준 SDK 통합이나 인증으로 표현하지 않는다.
- 이 표준의 파서·브리지·검증 SDK 통합·인증은 기본 구현 범위에 포함하지 않는다. 전체 문서 암기보다 어떤 문제를 해결하는 계약인지 먼저 학습한다.
- 광고 지연을 볼 때 요청·소재 준비·표시·첫 프레임을 구분하고, 형식별 메모리·플레이어 수·앱 진입 지연을 관찰한다. 모든 지표를 측정 시스템으로 구현할 필요는 없다.

## 문제를 중심으로 한 학습·개선 주기

1. **문제와 책임:** 누가 어떤 상황에서 불편·오류를 겪는지, SDK가 맡을 책임과 호스트·서버의 책임을 적는다.
2. **가설과 대안:** 원인 가설과 서로 다른 해결 대안을 검토한다. 비교할 가치가 있는 차이가 있을 때만 실험을 추가한다.
3. **작은 실험:** 검증할 질문 하나와 관찰 기준을 정하고, 필요한 최소 코드·대역·시연으로 확인한다.
4. **증거와 한계:** 실제 실행 조건·결과·반례·미검증 범위를 기록한다. 음성 결과와 기각한 가설도 보존한다.
5. **개선과 문서:** 채택·수정·보류·폐기를 판단하고 관련 요구사항·SDK 계약·학습 계획을 갱신한다.

학습 실험은 현재 문제와 연결된 범위로 제한하되, 기존 지침의 단순성·최소 변경을 이유로 필요한 비교나 구조 개선을 금지하지 않는다. 동작 확인 후에는 사용자가 선택 이유와 한계를 스스로 설명할 수 있는지도 확인한다.
