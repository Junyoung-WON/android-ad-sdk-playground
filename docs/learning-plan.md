## 선택 기능: 프리로드

사용자는 표시 지연을 줄이는 프리로드에 관심을 보였고, 기본 기능 이후 여유가 있을 때 추가하기로 했다. 필수 범위를 밀어내며 먼저 구현하지 않는다.

### 학습한 효과와 한계

- 광고 요청과 자원 준비를 광고 표시 시점보다 앞당겨 대기 시간을 줄인다.
- JSON만 미리 받으면 이미지 로드 지연은 남을 수 있다. 무엇을 준비해야 완료인지 정의해야 한다.
- 렌더링 시간까지 0이 되는 것은 아니다.
- 사용자가 로드 완료 전에 이탈하는 상황을 줄여 노출 기회를 확보할 수 있지만, 노출·수익 증가를 보장하지는 않는다.
- 광고 없음·입찰 불참 문제를 해결하지 못한다.
- 사용하지 않는 광고를 미리 준비하면 네트워크·메모리·준비 작업을 낭비할 수 있다.

### 최소 구현 제안

첫 배너 구현에서 사용자의 선택에 따라 `load()`와 `show()`를 분리했다. 현재 View 한 개가 로드 완료된 광고를 보관하는 계약이며, 화면과 분리한 프리로드·만료·소비 정책이나 성능 비교까지 구현한 것은 아니다.

- 광고 지면 하나·준비된 광고 한 건·메모리 보관으로 제한한다.
- 로드와 표시를 분리하고, 준비 중이거나 유효한 광고가 있으면 중복 준비 요청을 막는다.
- Activity·View를 장기 캐시하는 대신 화면과 분리한 광고 데이터·이미지 자원 보관을 우선 검토한다.
- 유효 시간, 소비·폐기 기준, 취소 후 늦은 응답을 반영하지 않는 정책을 정한다.
- 준비된 광고가 없거나 만료된 경우 일반 로드로 전환하는 방식을 제안했다.
- 한 번의 표시에 사용한 뒤 캐시에서 제거하는 정책을 제안했으나, 모든 광고 형식의 공통 규칙으로 일반화하지 않는다.
- 다른 SDK의 만료 시간은 그 제품의 정책이다. 예를 들어 특정 Google 광고 형식의 1시간을 우리 배너의 공통 표준으로 복사하지 않는다.
- 여러 지면·여러 건 캐시, 자동 보충·재시도, 디스크 보관은 기본 범위에 넣지 않는다.

### 검증

- 동일 광고·응답·이미지·지연 조건에서 프리로드 유무에 따른 화면 진입 → 표시 완료 시간을 비교한다.
- 준비 시간과 네트워크 작업이 앞선 시점으로 이동했다는 점을 함께 기록한다.
- 준비 완료 전 진입과 완료 후 진입을 구분한다.
- 미표시 광고의 노출 미발생, 만료·사용 후 재사용 방지, 취소·중복 호출을 검증한다.
- 실제 측정하지 않은 단축 수치나 노출·수익 증가를 이력서에 쓰지 않는다.

## 구현하며 학습할 개념

학습은 광고 공급·거래의 전체 흐름에서, 앱 안의 광고 경험과 SDK의 책임으로 초점을 옮긴다. 아래 형식별 주제는 후속 학습 대상이며 기본 구현의 자동 확장을 의미하지 않는다.

| 개념 | 이번 프로젝트와의 연결 |
| --- | --- |
| Android Library와 AAR | 다른 앱에서 사용할 수 있는 SDK 구성·연동 |
| 공개 API와 내부 구현 분리 | 사용자에게 필요한 기능만 노출하고 연동 계약 정의 |
| Context·View·생명주기 | 화면에 종속된 자원과 SDK 작업의 수명 관리 |
| Coroutines·취소·동시성 | 비동기 로드, 중복 호출, 해제 후 늦은 결과 제어 |
| 상태 모델 | 요청·로드 준비·광고 표시·해제, 필요시 재생·전체 화면 상태와 트래킹 상태 구분 |
| HTTP·직렬화·이미지 로드 | 광고 공급 과정과 실패 원인 분리 |
| 이벤트 식별·중복 억제 | 노출·클릭의 의미와 발생 단위 정의 |
| 의존성 주입·대역 | 서버·이미지 준비·시간·이벤트 전송을 통제하는 테스트 |
| 단위·통합·UI 테스트 | 정책 로직과 실제 연동 흐름을 각각 검증 |
| 문서와 샘플 앱 | SDK를 처음 쓰는 개발자의 연동 경험 개선 |
| R8 호환성 | 여유가 있으면 R8 활성화 샘플 앱에서 실행 검증 |
| 캐시·만료·소비·측정 | 프리로드를 추가할 때 학습 |
| 표시 위치·표현 방식·소재 종류 | 배너·카드·팝업·스플래시·동영상을 서로 배타적인 타입으로 단정하지 않음 |
| 재생 상태와 이벤트 | 준비·버퍼링·첫 프레임·재생·완료·오류의 구분을 후속 학습 |
| 앱 진입 제어와 종료 계약 | 정적 스플래시를 검토할 때 늦은 응답·제한 시간·중복 종료 경합 분석 |
| 관찰 가능성 | 요청·광고 표시 건을 연결한 이벤트 순서와 실패 원인 확인 |

필요한 경우에만 소비자 keep 규칙을 추가하고 범위를 좁힌다. 프로젝트를 복잡하게 만들기 위한 프레임워크·모듈 분할·추상화는 피한다.

### 1. 광고 형식을 바라보는 관점

공고의 형식 이름은 표시 위치·표현·타이밍·소재를 함께 나열한 것일 수 있다. 예를 들어 동영상이 카드나 전체 화면 안에 들어갈 수 있다. 실제 조합과 제품 정의는 별도로 확인한다.

| 형식·관점 | 학습할 문제와 질문 | 토이 프로젝트 적용 |
| --- | --- | --- |
| 배너 | 크기·비율·레이아웃, 화면 밖 이동, 재부착·재사용, 노출 단위 | 기본 구현. 정교한 가림 판정은 제한 명시 |
| 카드·네이티브 형태 | 앱이 구성하는 UI와 SDK의 계측 책임, 클릭 영역, 광고 표시·필수 자산, 목록 재활용 시 리스너·광고 바인딩 | 학습·시나리오 검토. 공고의 카드가 Native Ad라는 보장은 없음 |
| 팝업·전체 화면 | 중복 표시, 닫기·뒤로 가기, 광고 표시 실패, 창·Activity 수명, 클릭 후 복귀 | 종료 이유와 표시 권한을 후속 학습 |
| 스플래시·앱 진입 시 광고 | 준비 기한, 광고 없음·실패 시 콘텐츠 진입, 늦게 도착한 광고, 복귀 시 재표시, 스킵·종료 경합 | 정적 이미지로 한정한 확장 후보 |
| 동영상 소재 | 첫 프레임, 버퍼링·재생 상태, 비율, 음소거·오디오 포커스, 배경 전환·복귀, 진행률 계측, 플레이어 해제 | 우선 학습. 구현은 제한된 확장 후보 |

### 2. 모든 형식에서 검토할 SDK 계약

다음은 제품 설계 시 명시할 항목이다. 정답을 먼저 고정하기보다 최소 범위에 맞는 정책과 이유를 정한다.

1. **로드 준비·광고 표시 계약:** 로드 성공이 무엇까지 보장하는지, 광고 표시 가능 여부와 광고 표시 실패를 어떻게 알리는지 정의한다. 이미지 전체 준비 정책을 동영상 전체 다운로드 정책으로 확대하지 않는다.
2. **상태별 허용 동작:** 준비 중 재요청, 표시 중 다시 표시, 해제 후 호출의 동작을 정한다. 하나의 `isLoaded`로 모든 상태를 대표하지 않는다.
3. **요청 경합:** 이전 요청의 늦은 결과가 새 요청을 덮어쓰지 않게 한다. 요청 세대·작업 식별 또는 취소 등을 필요에 맞게 선택한다.
4. **콜백:** 같은 로드 시도의 성공·실패가 중복 전달되지 않도록 정의한다. 닫힘·완료·오류·표시 기회 포기는 의미가 다르며, 정해진 종료 결과를 중복 전달하지 않는 정책을 검토한다. 해제 시 콜백을 없애는 계약과 앱 진입 완료 계약을 혼동하지 않는다.
5. **스레드·소유권:** 공개 API의 호출 스레드, UI 변경·콜백 스레드, SDK 작업·View·타이머·플레이어의 소유자와 해제 시점을 문서화한다. 메인 스레드에서 네트워크·이미지 디코딩 등 무거운 일을 수행하지 않는다.
6. **앱 흐름 보호:** 광고 없음·오류·기한 초과가 콘텐츠 이용을 무기한 막지 않도록 정책을 정한다. 광고를 표시할 시점의 선택과 실제 앱 내비게이션은 매체 앱의 책임으로 유지한다.
7. **이벤트 의미:** 로드·광고 표시·노출·재생·완료·클릭·이동 결과를 구분한다. 내부 디버그 이벤트, 호스트 콜백, 서버 트래킹을 분리하고 식별자로 연결한다.
8. **확장 경계:** 실제 공통 동작만 공유한다. 하나의 거대한 광고 클래스에 영상·스플래시의 모든 조건을 넣거나, 반대로 아직 쓰지 않는 형식별 인터페이스를 미리 만들지 않는다.

### 3. 동영상에서 추가로 학습할 것

- `STATE_READY`는 실제 재생·첫 프레임·노출과 같지 않다. Media3에서는 재생 의도와 재생 억제 상태도 실제 재생 여부에 영향을 준다.
- 준비 완료, 첫 프레임 렌더링, 실제 재생, 버퍼링, 일시정지, 완료, 오류를 구분한다. 한 상태 신호를 모든 광고 이벤트로 복사하지 않는다.
- 25%·50%·75%·완료 같은 진행 이벤트를 다룬다면 기준을 정의한다. 단순 벽시계 경과 시간을 시청 시간으로 간주하지 않고, 버퍼링·정지·탐색·재생 반복의 영향을 검토한다.
- 첫 시작과 재개, 건너뛰기·사용자 닫기와 끝까지 재생 완료를 구분한다. 중도 오류나 해제를 정상 완료로 계측하지 않는다.
- 앱이 보이지 않거나 카드가 화면 밖으로 이동했을 때 영상·오디오를 어떻게 다룰지 정한다. 복귀 시 재개 여부와 오디오 포커스·음소거 정책은 별도다.
- 플레이어·Surface·리스너·진행률 관찰 작업의 수명과 해제를 다룬다. 목록의 여러 광고가 동시에 플레이어를 점유하는 문제를 이해한다.
- 플레이어 라이브러리의 신호를 광고 도메인 이벤트로 옮기는 역할을 구분한다. 검증된 플레이어·이미지 라이브러리를 사용하는 것은 가능하며 디코더를 직접 만드는 것이 목적이 아니다.
- 확장 구현을 선택한다면 고정 MP4 한 건, 단일 표시 위치, 기본 재생·오류·해제로 제한하고 나머지는 후속 항목으로 둔다. 이는 구현 확정이 아니다.

### 4. 스플래시에서 추가로 학습할 것

- Android 시스템 시작 화면, 앱의 로딩 화면, 그 위에 표시하는 광고의 수명은 구분한다. 공고의 스플래시가 어떤 제품 동작인지 확인하기 전에는 특정 SDK 형식을 그대로 대입하지 않는다.
- 콜드 스타트와 웜 스타트·포그라운드 복귀의 차이, 광고 표시 자격이 있는 Activity·화면을 학습한다.
- 광고 로드 제한 시간, 표시 가능 기한, 표시 후 노출 유지·스킵 가능 시간, 캐시 만료는 서로 다른 시간이다.
- 앱 콘텐츠 준비 완료·광고 로드 완료·대기 기한·사용자 스킵 등이 경합할 때 결과를 정한다. ‘기한 초과 → 콘텐츠 진입 → 늦은 응답 → 갑작스러운 광고 표시’를 대표적인 금지 시나리오로 제안한다.
- 콘텐츠 진입은 호스트 앱이 수행한다. SDK가 종료·건너뜀·실패 등을 알리는 방식과 호스트가 진입을 중복 수행하지 않는 방식을 각각 정의한다.
- 카운트다운이 있다면 의미를 정하고, 대기 기한은 단조 시간 기준과 제어 가능한 시계로 검증하는 방식을 검토한다. 화면의 숫자 감소만으로 타이밍 정확성을 판단하지 않는다.
- 광고 클릭으로 외부 앱을 다녀온 복귀가 새 스플래시 광고의 트리거가 되는 문제, 회전·화면 재생성·전체 화면 중복 표시를 검토한다.
- 확장 구현은 정적 이미지·명시적인 최대 대기·종료 결과 한 번 전달 정도로 한정할 수 있다. 대기 시간 수치는 아직 정하지 않았다.

### 5. 형식과 상태를 조합한 검증

고정 개수의 테스트를 목표로 삼기보다 사용자 동작·플랫폼 이벤트·비동기 결과가 만나는 지점을 선택한다. 기본 배너의 실제 테스트와 미구현 형식의 검토 시나리오를 구분한다.

| 상황 | 확인할 성질 | 적용 |
| --- | --- | --- |
| 첫 요청 지연 중 두 번째 요청이 완료됨 | 늦은 첫 결과가 현재 광고·콜백을 덮어쓰지 않음 | 공통 계약 확정 후 기본 범위 |
| 노출 후 스크롤·재부착·복귀 | 정한 동일 표시 건 기준으로 중복 계측되지 않음 | 배너·카드 |
| 해제와 로드 완료가 경합 | 해제된 View·콜백을 갱신하지 않음 | 기본 범위 |
| 제한 시간 직전·정각·직후에 광고 도착 | 뒤늦은 표시와 중복 콘텐츠 진입이 없음 | 스플래시 확장 시 |
| 로드됐지만 재생 전 정지·버퍼링 | 시작·진행·완료 이벤트를 허위 발생시키지 않음 | 동영상 확장 시 |
| 재생 도중 화면 종료·오류 | 정상 완료로 기록하지 않고 자원을 정리함 | 동영상 확장 시 |
| 외부 연결 페이지에서 복귀 | 의도하지 않은 전체 화면 광고 재표시가 없음 | 전체 화면 확장 시 |

실제 시간 지연을 기다리는 테스트 대신 필요한 경우 시계·디스패처·서버 응답·플레이어 신호를 제어한다. 실제 기기·에뮬레이터에서는 배치·클릭·생명주기 등 통합 동작을 별도로 확인한다.

### 6. 표준과 운영 관점의 후속 학습

- **VAST:** 동영상 광고를 전달하는 XML 응답과 플레이어 동작·트래킹의 계약을 이해한다. MP4 URL을 직접 재생하는 것만으로 VAST 지원이라고 표현하지 않는다.
- **MRAID:** 앱 내 리치 미디어 소재와 네이티브 컨테이너의 상호작용을 위한 인터페이스를 이해한다. WebView 사용 자체가 MRAID 구현은 아니다.
- **OM SDK:** 외부 측정 사업자의 조회 가능성·검증 측정을 돕는 역할을 이해한다. 자체 가시 영역 계산을 표준 SDK 통합이나 인증으로 표현하지 않는다.
- 이 표준의 파서·브리지·검증 SDK 통합·인증은 기본 구현 범위에 포함하지 않는다. 전체 문서 암기보다 어떤 문제를 해결하는 계약인지 먼저 학습한다.
- 광고 지연을 볼 때 요청·소재 로드 준비·광고 표시·첫 프레임을 구분하고, 형식별 메모리·플레이어 수·앱 진입 지연을 관찰한다. 모든 지표를 측정 시스템으로 구현할 필요는 없다.

## 문제를 중심으로 한 학습·개선 주기

1. **문제와 책임:** 누가 어떤 상황에서 불편·오류를 겪는지, SDK가 맡을 책임과 호스트·서버의 책임을 적는다.
2. **가설과 대안:** 원인 가설과 서로 다른 해결 대안을 검토한다. 비교할 가치가 있는 차이가 있을 때만 실험을 추가한다.
3. **작은 실험:** 검증할 질문 하나와 관찰 기준을 정하고, 필요한 최소 코드·대역·시연으로 확인한다.
4. **증거와 한계:** 실제 실행 조건·결과·반례·미검증 범위를 기록한다. 음성 결과와 기각한 가설도 보존한다.
5. **개선과 문서:** 채택·수정·보류·폐기를 판단하고 관련 요구사항·SDK 계약·학습 계획을 갱신한다.

학습 실험은 현재 문제와 연결된 범위로 제한하되, 기존 지침의 단순성·최소 변경을 이유로 필요한 비교나 구조 개선을 금지하지 않는다. 동작 확인 후에는 사용자가 선택 이유와 한계를 스스로 설명할 수 있는지도 확인한다.

### 첫 배너에서 사용자가 주도할 검토 — 제안

사용자는 지금까지 주로 질문에 답변했으며, 구조·흐름·개념을 이해하고 직접 검증하기 위한 역할을 요청했다. 아래는 협업 방식 제안이며, 사용자 검토·학습·테스트가 이미 완료됐다는 기록이 아니다.

- 사용자 역할: 해결할 문제와 기대 동작을 자신의 말로 정하고, 초기 API·재요청·해제 정책의 적합성, 구현의 계약 충족, 검증의 충분성을 판단한다. AI는 대안 설명·구현·조사·검증을 지원한다.
- 읽기 순서: 요구사항에서 기대 결과를 먼저 적고 샘플 연동 → `BannerAdView` → `BannerLoadSession` → HTTP·이미지 준비 경로를 따라간다. 정상 흐름 하나와 취소 경로 하나를 입력·스레드·자원 소유자·콜백·결과로 설명해 본다.
- 검증 방식: 실행 전에 결과를 예측하고 관찰값과 비교한다. 실제 화면 회전·이동·복귀는 현재 자동 테스트의 공백이므로 직접 검토할 후보로 둔다. 모의 서버의 `slow`는 8초 지연·SDK 호출 제한은 5초이므로, 제한 시간 이전의 응답 경합을 보려면 별도의 더 짧은 지연 조건을 마련한다.
- 테스트 검토: 단위 테스트의 준비 대역과 실제 Android 디코딩·View 검증을 구분한다. 코드·테스트·문서가 같은 잘못된 가정을 공유할 수 있음을 고려하고, 사용자 시나리오에서 기대 결과를 독립적으로 도출한다.
- 직접 수행할 작은 작업: 화면 수명 등 의문 하나를 선택해 기대 결과 → 재현 → 원인 가설 → 필요한 변경 또는 유지 판단 → 회귀 검증 → 기록까지 한 번 이어간다. 학습을 증명하려고 의도적으로 불필요한 구조 변경을 만들지는 않는다.
- 검토 산출물: 짧은 흐름 설명, 정책에 대한 판단과 이유, 실제 수행한 시나리오·결과·남은 한계. 자신의 이해·관찰을 바탕으로 현재 기능을 `main`에 반영할지 판단하는 것을 제안한다.

### 첫 코드 검토의 보완 — 실행 위치와 소유권

사용자가 기대 동작·정상 흐름 초안과 일부 테스트 설명을 작성해 검토를 요청했다. 아래는 현재 코드와 Coil 2.7.0 기본 설정을 확인한 설명이다. 이후 사용자는 광고 데이터 응답 대기 중 회전과 HTTP 취소 핸들러 실행을 관찰했으며, 그 범위·한계는 [D-008](decisions.md#d-008--사용자의-로딩-중-회전-관찰과-취소-경로-검토)에 기록했다.

| 단계 | 실행 위치 | 보관·해제 책임 |
| --- | --- | --- |
| View.load → Session.load → prepare 진입 | Main.immediate. suspend 함수 호출만으로 Default로 전환되지 않음 | View가 Scope를 소유하고 세션에 주입. 세션은 요청 Job·세대·로드 완료된 광고 참조를 관리 |
| HTTP 입력 검증·enqueue | 호출한 Main에서 입력·URL 구성, 통신은 OkHttp에 등록 | HttpSource는 주입된 client를 사용. 진행 Call의 취소는 코루틴 취소와 연결 |
| HTTP 콜백·상태 확인·본문 읽기 | OkHttp 작업 스레드 | 응답은 HttpSource의 response.use 블록에서 닫음. body 문자열은 처리 중의 지역 데이터 |
| JSON 파싱·필드 검증 | withContext(Default), 완료 후 호출한 Main으로 복귀 | BannerCreative를 반환하며 HttpSource가 계속 보관하지 않음 |
| 이미지 준비 | Main에서 ImageLoader 호출. Coil 내부 fetch·decode 기본 실행 위치는 IO, 완료 후 Main으로 복귀 | 어댑터는 ImageLoader를 빌려 쓰고 Drawable을 반환. 생성·shutdown 책임은 View에 있음 |
| 로드 완료된 광고 저장·onLoaded | Main | 세션 prepared에 광고 정보와 Drawable을 담은 로드 완료된 광고를 보관. 샘플은 광고 표시 버튼을 활성화하며 View 가시성을 바꾸지 않음 |
| show | Main | 인자는 없는 공개 API. 세션이 저장한 결과를 render 콜백에 전달하고, View의 ImageView도 같은 Drawable을 참조 |

소유권은 동작 수행자와 함께 **누가 생성·보관하고, 교체·취소·해제 시점을 결정하는가**를 적는다. 호출한 객체가 모든 반환 데이터나 주입 의존성을 영구 소유한다고 보지 않는다. 현재 최상위 사용 기간은 호스트 Activity, SDK 자원은 BannerAdView, 요청 Job·로드 완료된 광고는 세션이 책임진다. 세션은 주입 Scope 전체를 취소하지 않으며 View가 scope.cancel()을 호출한다.

`destroy()`는 최종 해제다. 별도 취소 콜백이나 단순 '로딩 중단' 상태를 내보내지 않는다. 객체·이미지를 즉시 메모리에서 삭제하는 것이 아니라 작업·명시적 자원을 정리하고 참조를 제거한다. 참조 해제 후의 메모리 회수는 GC와 라이브러리의 수명 관리에 따른다. 서버가 이미 받은 요청의 처리가 반드시 중단되는 것도 아니다.

보이지 않거나 detach된 View도 메모리에 존재할 수 있다. 현재 `show()`는 이미지 바인딩 가능 여부만 반환하며 가시성을 검사하지 않는다. 준비됐고 해제되지 않았다면 true일 수 있다. 로드·광고 표시·노출이라는 표현을 구분한다.

### 테스트를 빠르게 읽는 순서

- 한글 테스트 이름에서 조건·동작·결과를 확인한 뒤 assert가 실제로 무엇을 관찰하는지 먼저 읽는다. 이후 대역·입력·실행 순서가 그 조건을 만드는지 역으로 확인한다.
- '요청을 안 보냄'은 requestCount 같은 증거, '응답을 거부함'은 요청 이후 INVALID_RESPONSE 같은 증거가 필요하다. 같은 표현으로 섞지 않는다.
- 단위 테스트의 문자열 준비 대역은 실제 PNG 디코딩·화면 렌더링을 검증하지 않는다. 기기 테스트의 Drawable 반영도 표준 노출 측정이나 최종 화면 픽셀 검증을 대신하지 않는다.
- 세션 → HTTP 소스 → 기기 연동 순서로 읽고, 한 번에 한 시나리오만 실행한다. 새 기기 테스트는 응답을 gate로 대기시킨 뒤 ActivityScenario.recreate()를 호출한다. 실제 방향 전환·가림·메모리 누수 검증과는 구분한다.

### 직접 수행할 회전 실험

SDK 내부에 delay를 넣지 않고 샘플 앱의 '광고 응답 지연'을 3~4초로 설정한다. 모의 서버는 delayMs 쿼리를 받아 광고 데이터 응답을 0~4000ms 늦춘다. 기존 slow 시나리오는 시간 초과 재현용 8초이므로 이번에는 '정상 이미지 배너'를 선택한다.

로드 시작 후 준비 완료 전에 화면을 회전해 화면 ID가 바뀌는지 확인한다. Logcat의 BannerSample 태그에서 이전 ID의 시작·종료(구성 변경=true), 새 ID의 생성을 확인하고 이전 종료 뒤에 이전 ID의 성공·실패 콜백이 없는지 관찰한다. 회전 이전에 이미 성공했다면 해당 실행은 '로딩 중 회전' 증거로 삼지 않는다. 새 화면은 미로드 상태이며 자동 재요청하지 않는다. 지연값은 복원된다. 새 화면에서 직접 로드·광고 표시해 재사용이 가능한지 확인한다.

원래 서버를 실행한 채 코드를 고쳐도 자동 반영되지 않으므로 서버를 재시작해야 한다. 포트 충돌 시 다른 포트와 동일한 ADB reverse·앱 주소를 사용한다. 실행 절차는 [README](../README.md)를 따른다.

사용자는 위 실험에서 이전 화면 종료·새 화면 미로드 상태·HTTP 취소 핸들러 로그를 관찰했다. 이는 현재의 명시적 해제 계약을 평가할 근거다. 서버 측 처리 중단·이미지 단계 취소·GC·누수 없음까지 같은 실험의 결과로 확대하지 않는다. 회전 중 로드 유지와 비가시 시 취소는 현재 계약의 결함으로 확정하지 않고 별도 요구와 수명 설계로 검토한다.

참고: [Android Activity 생명주기](https://developer.android.com/guide/components/activities/activity-lifecycle), [Coil 2.7.0 기본 실행 컨텍스트](https://github.com/coil-kt/coil/blob/2.7.0/coil-base/src/main/java/coil/request/DefaultRequestOptions.kt).

### 마감 전 검토 범위 조정 — 제안

사용자는 위임한 구현·설계의 흐름과 객체를 이해하는 검토 비용이 예상보다 크고 지원 마감까지 정리할 수 있을지 우려했다. 검토 시간만으로 역량 부족을 판단하지 않는다. 첫 학습·타인이 작성한 코드 이해·정책 검토가 함께 진행되는 상황이며, 이전에 큰 구현 단위를 한꺼번에 전달한 협업 방식도 검토 부담의 요인으로 본다. 후속 답변으로 11/29 23:59 마감과 지원 자료 작업을 포함한 총 36~40시간의 가용 시간이 확인됐다.

- 우선 깊게 볼 범위: BannerLoadSession의 준비·요청 교체·늦은 결과 차단, BannerAdView의 표시·해제와 호스트 onDestroy 연결. 한 경로를 동작 예측 → 코드·테스트 근거 → 실제 관찰로 확인한다.
- 경계로 확인할 범위: HTTP·이미지 어댑터의 입출력·오류 분류·응답 닫기·취소 전달. 필요한 설정과 사용 계약을 확인하고, 라이브러리 내부 코드는 질문이나 실패를 좁힌 뒤 읽는다.
- 후속 탐구: 디코더·연결 풀 등의 내부 구현, 모든 함수의 줄별 해설, 반복된 상세 정리. 현재 위험과 연결되지 않는 조사까지 첫 검토의 완료 조건으로 삼지 않는다.
- 검토 중단 기준 제안: 핵심 API 보장·재요청/해제 결과·자원 정리 경로를 자신의 말로 설명하고, 정상·대표 실패·로딩 중 회전의 예상/실제 결과와 남은 질문을 기록하면 다음 판단으로 넘어간다. 시간 제한은 실력 평가가 아니라 조사 범위를 조절하는 장치로 사용한다.
- 마감 대응 제안: 현재 기능의 검증·README·지원 자료 초안을 우선 묶는다. 새 형식·프리로드·재로드 유지 정책은 여유를 확인해 선택한다. 노출·클릭 미구현 등 한계를 명시하며 전체 프로젝트의 장기 목표와 이번 지원 시점의 결과물을 구분한다. 제출 준비 시간을 먼저 확보한 뒤 남은 시간으로 구현 범위를 정한다.
- 협업 조정 제안: 핵심 정책 하나·관련 주요 파일 1~2개·대표 검증 경로로 작업을 나눠 전달한다. 사용자는 예상·판단을 제시하고 AI는 필요한 설명·반례·구현을 지원한다. 이 방식과 세부 시간 배분은 아직 사용자 합의로 기록하지 않는다.

### 이번 지원 마일스톤의 36시간 배분 — 제안

사용자가 제공한 총 36~40시간에는 포트폴리오 작업도 포함돼 있다. 아래는 36시간을 기준으로 잡은 작업 예산이며 완료 소요 시간 보장이나 확정 일정이 아니다. 최대 4시간의 추가 여유는 예비로 둔다.

| 작업 | 시간 예산 | 남길 결과 |
| --- | --- | --- |
| 현재 배너 직접 검토·실험 | 6시간 | 핵심 API·수명 경로 설명, 정상·대표 실패·회전 관찰, 검토 판단 |
| 사용자 문제 개선 한 건 | 8시간 | 정책 비교 → 작은 구현 → 회귀 검증 → 실제 결과. 후보는 재로드 중 기존 광고 유지 |
| README·연동 절차·짧은 시연 | 3시간 | 재현 가능한 실행 절차, 구현 범위·한계, 시연 |
| 포트폴리오·이력서 | 10시간 | 프로젝트 설명 1~2페이지와 이력서 반영. 본인이 수행한 판단·실험과 AI 지원 범위 구분 |
| 설명·면접 대비 | 3시간 | 문제·선택·검증·한계를 자신의 말로 설명 |
| 예비·제출 점검 | 6시간 | 결함·환경 문제 대응, 파일·링크·지원 제출 확인 |
| 합계 | 36시간 | 지원 자료 시간을 포함한 전체 예산 |

- 사용자 개선 문제는 현재 흐름에 연결된 한 건을 우선한다. 새 광고 형식·프리로드·노출·클릭 트래킹 전체를 이번 마감의 필수 완료 조건으로 동시에 추가하지 않는다. 미구현 범위는 지원 자료에 명시한다.
- 현재 기능 검토의 6시간은 모든 줄을 완전히 이해하는 목표가 아니다. API 결과 예측·주요 수명 경로·대표 실험·중요한 미해결 문제 식별까지를 우선한다.
- 개선 한 건에는 설계·사용자 이해·구현·검증·기록이 모두 포함된다. 예산을 넘겨 핵심 결함이 남으면 검증된 기존 범위로 지원 자료를 구성하고 미완료 개선은 후속 과제로 구분한다.
- 날짜별 제안: 11/24까지 현재 기능 검토를 우선하고, 11/26까지 기능 범위를 확정한다. 지원 자료 초안은 검토와 병행해 시작하며 11/28에는 제출 가능한 상태를 만든다. 11/29는 제출·오류 대응 여유로 남긴다.
- 장기 목표인 광고 SDK 문제 해결 경험은 지원 이후에도 계속한다. 지원 전 결과물의 범위와 전체 학습 완료를 동일한 기준으로 묶지 않는다.

### 재로드 개선에서 확인할 소유권과 동작

현재 feat/retain-banner-on-reload에서는 표시 중인 이미지와 로드는 완료됐지만 아직 View에 반영하지 않은 광고를 구분한다. API 계약은 [적용 계약](requirements.md#재로드-중-기존-광고-유지와-광고-표시-결과--적용), 재현 상태는 [D-010](decisions.md#d-010--재로드-중-기존-광고-유지의-검증-기준)을 따른다.

검토할 핵심은 A 표시 → B 로드 → B 준비 완료 → B show → destroy 순서에서 ImageView.drawable과 Session.prepared가 각각 무엇을 참조하는지 예측하는 것이다. prepared를 비워도 ImageView의 A 참조가 남을 수 있으며, B를 표시하면 ImageView의 참조가 바뀐다. 참조 교체와 Bitmap 메모리의 즉시 회수는 구분한다. 새 show의 성공 의미와 기존 A의 표시 유지 여부도 별개로 판단한다.

사용자는 공개 View.show와 내부 Session.show의 성공 의미를 다르게 둘 수 있는지 질문했다. 검토할 순서는 SDK 호출자가 반환값으로 무엇을 판단해야 하는지 정하고, 그 계약에 맞게 내부 함수의 책임과 이름을 정하는 것이다. 내부 세션의 반환값이 공개 API 정책을 자동으로 결정하는 것은 아니다. 당시 Session.show와 현재 bindPrepared 모두 상태 조회만 수행하지 않고 render를 호출하므로, 준비 상태 조회와 이번 호출의 이미지 반영 결과를 구분한다.

### SDK 호스트의 시나리오로 show 계약 비교하기

아래는 이번 프로젝트의 대안을 평가하기 위한 가상 사용 시나리오다. 실제 광고 플랫폼 공통 정책으로 보지 않는다.

| 앱의 목적 | 필요한 정보 | 최신 반영만 성공 | 기존 광고 유지도 성공 |
| --- | --- | --- | --- |
| 피드 하단에 광고가 없을 때만 영역 접기 | View에 광고 내용이 있는가 | show 결과 외에 내용 존재 조회 필요 | show 직후 true면 내용 유지 가능. 기존/새 광고는 구분 안 됨 |
| 페이지 전환이 끝난 시점에 새로 로드 완료된 광고 반영 | 가장 최근에 로드 완료된 광고를 이번에 반영했는가 | show 반환으로 판단 | true만으로 판단 불가. 추가 정보 필요 |
| 갱신 실패를 기록하되 기존 광고 영역 유지 | 로드 실패 원인과 현재 내용 존재 | 로드 콜백과 내용 조회 조합 | 로드 콜백과 내용 조회 조합. show를 호출해 확인하면 다른 시점에는 교체 부작용 가능 |
| 광고를 바꾸지 않고 레이아웃만 결정 | 현재 내용 존재 | 별도 읽기 전용 조회 필요 | 별도 읽기 전용 조회 필요 |

현재 공개 API에는 내용 존재 조회가 없다. 유지 정책이 생긴 뒤에는 호스트가 성공한 show와 destroy 등을 추적해 상태를 복제할 수도 있지만, SDK가 이미 아는 정보를 호스트마다 다시 관리해야 한다. 읽기 전용 hasBoundAd는 이런 복제를 줄이기 위한 후보이며 구현 전이다. 실제 화면에 보이는지와 노출 집계는 따로 판단한다.

### 선택한 계약으로 직접 확인할 작업

2026-11-25 사용자는 가장 최근에 로드 완료된 광고 반영을 광고 표시 성공으로 선택했고, 상태 조회는 후속 기능으로 보류했다. 이전 Boolean 비교표는 선택을 위한 기록이며 현재 show는 성공/실패 콜백을 전달한다. 현재 계약과 자동 검증은 [D-011](decisions.md#d-011--기존-광고-표시-유지와-광고-표시-결과-콜백)을 따른다.

- A를 표시한 뒤 3초 지연으로 B를 로드한다. B 준비 전과 완료 후 show 전까지 A가 유지되는지 예측하고 확인한다. 광고 표시를 누르면 성공 콜백의 광고 ID가 바뀌는지 본다. 모의 서버의 그림은 같으므로 픽셀 차이를 기대하지 않는다.
- 광고 없음이나 이미지 준비 실패로 재로드한다. 로드 실패와 별개로 A가 유지되는지 본다. 광고 표시 실패 콜백은 기기 테스트에서 LOAD_FAILED와 loadError로 확인하며, 샘플 광고 표시 버튼은 로딩 중/실패 후 비활성화된다.
- BannerAdView의 준비 람다에서 광고 정보와 Drawable을 함께 만드는 이유, load에서 clearImage를 제거해도 세션의 prepared는 비우는 이유를 설명해 본다. destroy에서는 왜 둘 다 정리해야 하는지 연결한다.
- 성공 콜백은 이미지를 View에 설정한 뒤 show 호출 안에서 실행된다. 콜백을 쓴다는 이유만으로 비동기 실행이나 실제 노출 검증이 생기는 것은 아니다. 콜백 안에서 destroy해도 결과가 추가로 전달되지 않는 테스트를 읽어 본다.

### 반복 show를 노출 횟수로 해석하지 않기

준비된 A에 show를 여러 번 호출하면 성공 콜백도 여러 번일 수 있다. 이것을 노출과 수익 증가로 바로 연결하지 않는다. 현재는 노출 집계 자체가 미구현이며, 후속 설계에서는 SDK의 노출 조건 판정, 동일 제공 건 이벤트 생성 억제, 전송 재시도, 서버의 유효성 확인과 중복 제거를 구분한다. 특히 A를 표시한 채 B를 로드하기 시작해도 A의 노출 처리 이력을 초기화하면 안 되는 이유를 생각해 본다. 자세한 현재 상태와 검증 후보는 [D-012](decisions.md#d-012--반복-show와-노출-중복-방지의-경계)를 따른다.

광고 표시 리스너의 수명을 읽을 때는 함수 인자로 잠시 사용하는 참조와 멤버 변수에 보관하는 참조를 구분한다. show(listener)는 호출 안에서 콜백을 전달하며 리스너를 이후 이벤트에 사용하도록 등록하지 않는다. 호스트가 동일 객체를 계속 보관하거나 다음 show에 다시 전달하는 것은 별개다. 이 설명을 객체의 즉시 삭제나 메모리 누수 전체 보장으로 해석하지 않는다.

### 재로드 유지 구현 이후 우선순위 — 2026-11-25 제안

판단 기준은 광고 SDK의 핵심 기능인가, 실제 연동과 운영에서 생기는 문제를 다루는가, [기존에 제공받은 공고](project-context.md#지원-공고)의 담당 업무와 자격·우대 요건에 연결되는가다. 현재 빈 부분과 선행 의존성도 함께 고려한다. 공식 공고 페이지는 이번 조회 도구에서 열리지 않아 문서에 기록한 사용자 제공 원문 정리를 기준으로 판단했으며, 최신 공고 내용을 재검증했다고 주장하지 않는다. 아래 내용은 작업 순서 제안이며 새 기능 착수나 상세 정책 합의가 아니다.

| 순서 | 작업 | 최소 완료 기준과 판단 근거 |
| --- | --- | --- |
| 먼저 | 현재 기능 PR 검토와 병합 | A 유지와 B 교체, show 콜백 계약을 검토하고 원격 PR로 마무리한다. 현재 커밋 요청에는 푸시·PR 생성·병합이 포함되지 않는다. Git 협업과 API 변경 검토 경험으로 연결한다. |
| 1 | SDK의 노출 조건 판정과 동일 제공 건의 중복 이벤트 방지 | 노출 조건을 먼저 정하고, 아직 화면에 보이지 않는 광고는 제외한다. 반복 show와 A 표시 중 B 로드 실패가 A의 이벤트를 늘리지 않는지 확인한다. 광고 이미지 로더를 넘어 광고 SDK의 핵심 책임을 다루며 공고의 노출 로직 개발·검증에 직접 연결된다. |

각 기능에는 관련 한글 테스트, 샘플 앱의 재현 경로, API 문서 갱신을 함께 포함한다. 테스트나 문서를 모든 구현이 끝난 뒤의 별도 단계로 미루지 않는다. 현재 광고 표시 상태 조회와 회전 중 로드 유지, 프리로드는 사용처와 필요가 확인된 뒤 다시 판단한다.

지원 자료는 위 기능 목록의 마지막까지 기다리지 않고 지금부터 병행한다. 이미 완료한 재로드 문제의 재현과 정책 비교, 사용자 수동 관찰을 README 시연과 포트폴리오 초안에 연결한다. 가이드 앱과 문서화는 공고의 직접 담당 업무이며, 지원서 작업 시간을 새 기능에 모두 사용하지 않는다. 사용자가 처음 제시한 36~40시간은 전체 가용 예산이므로 지금 남은 시간으로 취급하지 않는다. 11/29 23:59 마감을 고려해 현재 결과물과 지원 자료를 먼저 제출 가능한 상태로 확보하고, 노출 판정 한 단위를 다음 우선 구현으로 제안한다. 이후 구현 수는 실제 남은 시간과 사용자의 이해·검토 상태에 따라 조절한다.
